上个世纪末，是计算革命爆发的时代，是科技百花齐放的时代，是工业文明开花结果的时代，并且这一切最终引领世界进入信息时代。那时是一个惜字如金的时代，硬盘存储容量以 MB 乃至 KB 为计量单位，高密的 5 1/4" floppy disk （5.25 英寸）容量才 1.2MB。更大容量的 CD-ROM（Compact Disc Read-Only Memory） 还在实验室研究中，早期也只是用来存储音频。1985 年，由 SONY 和飞利浦制定黄皮书标准后使得这种格式能够适应各种二进制数据，不过最终没流行几年，就被高容量的机械磁盘和基于电子陷阱原理的固态存储芯片替代。

These floppy disks were immensely popular back in the day with the low density variation being used in Apple, Atari, Commodore, and IBM compatible computers. Capacities ranged from 160KB up to 1.2MB for the high density disks.

Acronyms for some common 5 1/4" diskette types:

• SSDD => Single-Sided Double-Density, 164-184 KB
• DSDD => Double-Sided Double-Density, 360 KB
• DSQD => Double-Sided Quad-Density, 720K
• DSHD => Double-Sided High-Density, 1.2M

('SSDD' is sometimes given as 'SS DD', 'SS/DD', etc; so too for all the others.)

For a time after the 5 1/4" diskettes arrived they were called "minidiskettes". This term gradually faded from use when the earlier "standard size" 8" diskettes became less and less common.

At the beginning of the 90’s, the PC platform was often mocked by its rivals. PCs of that era had become much more powerful than, say, an Amiga 500. But the Amiga offered a flat memory address, while a DOS program could only access memory using cumbersome 64 KiB segments. And to add insult to injury, there was this strange 640 KiB memory limitation. No matter how much physical memory you had in your box, the utter most important Conventional Memory was limited to 640 KiB!

The Legend teaches us that Bill Gates once declared that “640 KB ought to be enough for anybody“, then designed MS-DOS to enforce this limitation.

• https://www.pcjs.org/documents/specs/dpmi/[DOS Protected Mode Interface (DPMI) Specifications]
• https://komh.github.io/os2books/[OS/2 Books]

比尔盖茨说：“640KB足够所有人使用”。所以 MS-DOS 从此只能使用 640KB 内存，即使 Intel 80386 这款划时代的 CPU 芯片问世。DOS 发迹时真正是 16bit 机器的时代，可以使用 16 条地址线寻址 2^16 + 1 = 65536 字节，因此受到 640KB 限制。80386 带来了两种工作模式：其中之一是继承 80286 的内存地址分页管理的保护模式（protected-mode），另一种是 Virtual 8086 虚拟模式，简称 V86 或虚拟 86。Virtual 8086 模式是在内存地址保护环境中模拟出的一个 16bit Real Mode machine 用于运行早期 8086/8088/80188 等等芯片上设计的程序，这些程序作为 V86 中的任务（V86 tasks）运行，与之相对的是运行于保护模式的 80386 tasks。V86 模式可以运行多个 V86 tasks，不仅有效利用新芯片的保护模式多任务（multitasking），还可以混合编程 V86 tasks 和 80386 tasks。参考 80386 Programmer's Reference Manual - Chapter 15 Virtual 8086 Mode。

DOS 和 Windwos 9x 引入了扩展内存管理器（XMS），HIMEM.SYS，Windows 9x 依赖它管理 640KB 以上内存。缺失会导致 WIN.COM 无法加载核心组件，系统卡在 DOS 实模式。Windows 95 使用了和传统 DOS 的启动链同名的文件，但是功能有变更：IO.SYS（集成化内核）替代的传统文件的 IO.SYS + MSDOS.SYS；而使用 MSDOS.SYS（启动配置文本）替代 DOS 系统的 CONFIG.SYS 配置文件。Windows 9x 直接在 IO.SYS 内置以下关键驱动，无需用户配置。但是 MSDOS.SYS 配置错误或 IO.SYS 程序损坏等等问题都会导致 Windows 不能加载 HIMEM.SYS 管理高位内存：

• HIMEM.SYS      (XMS 内存管理)
• IFSHLP.SYS     (文件系统助手)
• SETVER.EXE     (版本伪装)。

MS-DOS 系统继续打补丁，Intel/Microsoft 搞了一个 DOS PROTECTED MODE INTERFACE (DPMI) 规范以突破 16bit 系统的限制，640kb 真的不够用。DPMI 是一个双层架构，包括作为客户端的应用程序和提供服务的宿主（DPMI HOSTS）。DOS4GW 与 DPMI 是 DOS 系统突破 640KB 内存限制 的两种关键技术方案，二者在架构层级、实现机制和应用场景上存在根本差异。DOS4GW 作为 DPMI 客户端，通过 DPMI 服务访问保护模式功能。要特别强调 DOS4GW 的局限性——它是 Watcom 私有方案，仅支持 Watcom 编译的程序；而 DPMI 是通用接口，支持任何兼容 DPMI 的程序 (DJGPP, Borland 等)。更严重的问题是 DOS4GW 无内存隔离，多程序同时运行必崩溃（如 DOOM 运行时无法驻留 MOUSE.COM）。DPMI 规范则通过 INT 31h 中断实现硬件虚拟化，支持多任务（如 Windows 3.1 标准模式）。

可以使用 SYS 命令将系统盘所使用的引导文件传输到其它磁盘中，然后结合 xcopy 命令备份系统。SYS 传输的 io.sys msdos.sys command 三个文件外加磁盘的引导扇区就是最小的引导系统。注意，需要 xcopy 命令打开  /h /r 选项以覆盖只读的系统文件，否则 SYS 命令传输的只读系统文件 MSDOS.SYS 不会正确备份。MS-DOS 提供的 SYS 命令是 MS-DOS 中用于传输系统引导文件的核心工具，其设计目标是使软盘或硬盘成为可启动设备。SYS 命令是 DOS 时代的引导修复圣器，其通过精确控制 IO.SYS 的分段存储（保留扇区+簇2）和磁盘引导扇区签名，实现了在磁盘首个扇区 512 字节（内含磁盘分区表和主引导记录）限制下的系统引导。尽管在现代 UEFI 系统中已被取代，但其“内核分割加载”的设计思想仍存在于 Windows 10 的 bootmgr.efi + winload.efi 双文件架构中。掌握 SYS，就握住了理解 x86 引导进化史 的第一把钥匙。

SYS 命令的本质作用是通过调用 DOS 中断 0x21 的 0x3700 系列功能向目标磁盘写入引导系统的三个文件（按固定顺序），成功执行后，目标盘引导扇区末尾两字节被设为 0x55AA（标准引导签名）。

• IO.SYS：DOS 内核 + 硬件抽象层
• MSDOS.SYS：文件系统与进程管理（DOS 6.22 之前版本）
• COMMAND.COM：命令行解释器

运行 SYS 命令有几个的约束条件：

• 目标盘必须为空白根目录，ATTRIB -R -H -S IO.SYS 删除之，否则报错：No room for system...
• 源/目标盘文件系统一致， 可以用 FORMAT /S 初始化，否则报错：Incompatible system size
• IO.SYS 文件必须连续存储，可以运行 DEFRAG 整理磁盘，否则启动失败（Missing operating system） 

注意：Windows 95/98 的 SYS 会额外传输 WINBOOT.SYS 和 DRVSPACE.BIN。使用 FORMAT /S 命令等价与格式化后再执行 SYS 命令，不过 Windows 系统会像 MSDOS.SYS 写入一行注解，使用 `; SYS` 或者 `; FORMAT` 分别表示此引导系统的制作方式。可以使用 Windows 98 启动盘的 FDISK /MBR 命令重写主引导记录。要通过此引导系统进入 Windows 9x，就需要使用 Windows 自身的 MSDOS.SYS 文件。

MS-DOS 使用 8.3 文件名格式，这是 FAT12/16 文件系统的缺陷，没有长文件名（LFN, Long File Name) 存储能力。FAT32 内置支持长文件名，(VFAT 扩展)，并且兼容 MS-DOS，自动创建 FILENA~1.TXT 这样的 8.3 格式。如果使用 xocpy 拷贝备份系统，则后丢失长文件名。可以在 MS-DOS 7.x (Win9x) 中操作，使用 xcopy /h /k /c  等关键参数：

• /c → 忽略错误（避免因 LFN 中断）
• /h → 复制隐藏文件（LFN 存储为隐藏属性）
• /k → 保留文件属性（防止 LFN 记录被剥离），DOSBox 中对应为 /a （archive attribute set）

MS-DOS 6.22 环境下可以在 CONFIG.SYS 配置文件中安装 LFNDOS.SYS 驱动来解决。

DOS 引导系统的 FAT16 磁盘布局（经典结构）：

• 扇区 0 为引导扇区，512 字节，写入跳转指令 + BPB 表；
• 扇区 1-2 为保留扇区，1024 字节，存放 IO.SYS 第一部分；
• 扇区 3-4 (簇 2) 保存 IO.SYS 主体，大小可变，通过文件内容复制；
• 簇 3 保存 MSDOS.SYS，内容可变，通过文件内容复制；
• 根目录区保存 OMMAND.COM，内容可变，标准文件写入；

关键细节：IO.SYS 被分割存储 —— 文件头在保留扇区，主体在簇 2。这是为了兼容 BIOS 引导协议（BIOS 只能加载单个扇区）。


不得不提划时代的 Windows 95 操作系统，它奠定了 Windows 系列的用户界面基本结构，更重要的是带领操作系统从 16-bit 走进了 32-bit 时代！如今，操作系统早已跨入 64-bit 时代，但是从 Windows 95 开启的 32-bit 仍然是普通用户的主流配置。PCjs 提供的 Windows 95 Build 4.00.499 等等使用 3.5" floppy disks 软盘分发的介质，还有已经安装好的 Windows 95 Build 4.00.950，这是首发版。WinWorldPC 则提供了多个版本，包括支持 USB 的 Windows 95 OSR2.1 光盘镜像，此外还有 RTM (Released To Manufacturing) 和 Microsoft Windows 95B (4.00.1111.osr2) 3.5"-DMF (Distribution Media Format)。1996 年2月14日，微软发布 Windows 95 的第一个后续修正版本 OSR (OEM Service Release)，针对系统漏洞进行了大量的修补完善。六个月后 Windows 95 OSR2 版本带来了当时颇为先进的 FAT32 磁盘分区规范，以及 IE3.0 这坨浏览器。

DOSBox 或者 DOSBox-X 安装 Windows 95 OSR2 大概率出现问题，在完成所有文件拷贝后提示 Error SU992010，尝试由 Windows 3.1 升级安装也不行，Warning SU0168 警告后终止。安装 Windows 95 Update 版本似乎更适合 DOSBox 0.70/0.71。OSR2 还有 XMS Cache Error。但是通过 QEmu 或者 VMWare 安装好的系统镜像则可以在 DOSBox 正常加载运行。DOXBox-X 提供了 Reported DOS version 功能，不需要使用 DOSVER 等工具给 WIN.COM 打补丁，设置报告版本为 7.10 就可以满足 Windows 95 的运行条件。DOSBox 也可以使用 ver set 7 命令来设置。

Windows 95/98 作为基于 DOS 之上的系统，它对 DOS 版本有要求，WIN.COM 记录了版本号。WIN.COM 作为 16 位 DOS 可执行文件（MZ 格式），其头部包含关键字段：偏移 0x12-0x13：0x14 0x00（标识 Windows 95）或者偏移 0x16-0x17：0x33 0x00（标识 Windows 98）。Windows ME 变革后，取消实模式 DOS 启动（IO.SYS 不再暴露 DOS），DOSVER 机制失效。

Windows 95 和 Windows 98 都一样通过 DOS 系统加载图形界面，所以理论上可以通过 DOSBox 内置的 DOS 系统来引导图形界面。注意，Windows 95 没打补丁只支持 FAT，DOSBox 中将文件夹映射为磁盘时，需要设置 -fs fat 参数，否则安装程序无法写入文件。

DOSBox-X 支持将文件夹映射为 IDE 驱动器供 Windows 使用，例如 mount F "folder" -t dir -ide 2s 命令会对应模拟出一个 F_Drive 磁盘。但是文件夹大小不能超过 FAT32 的尺寸限制，同时文件不能与主机系统有访问冲突。DOSBox-X 会根据文件夹的大小来决定转换成 FAT16/32 的模拟磁盘。可以设置 convert fat free space 空闲空间大小来影响这个转换过程，默认设置有 250MiB 空间余量，只有文件夹大小加上这个余量不超出 2GiB，就会转换成 FAT16 磁盘格式，否则是 FAT32。使用 boot -convertfatro 或者配置 convert fat free space=0 可以让 DOSBox-X 映射只读的驱动器（ro = read-only）。Windows 9x 系统修改映射的磁盘后，数据并不会直接写入宿主的磁盘，而是的内存中暂存，需要通过 DOXBox-X Drive 菜单中对应的盘符来保存数据，这回将宿主磁盘的目录内容叠加 Windows 9x 中修改的内容写入一个磁盘镜像文件。

DOSBox-X 会按照 IDE 主从（master/slave）来为 Windows 设置盘符，但是也会按硬盘、光盘分类进行连续的盘符设置。以下脚本在 DOS 环境下会按指定的盘符加载，但是进入 Windows 系统后会将光盘的盘符调整到硬盘后面。测试中发现，同时设置四个 IDE 设备时，配置方式不同可能导致只有前三个有效，需要考虑 [ide, primary] 和 [ide, secondary] 配置项来设置。

== DOSBox-X’s Mapper Editor

DOSBox 设计了一个以事件驱动的输入控制器，通过设定事件与输入的映射关系就可以任意定制键盘、鼠标、摇杆等设备的输入功能。

DOSBox-X 提供了 mapper editor 来修改输入映射，可以通过主菜单 Main -> mapper editor 或者命令行参数 -startmapper 来打开它。编辑器中展示了一个虚拟键盘，还包括鼠标 Mouse L M R 三个按键，还有摇杆用 X- X+ Y- Y+ 等等表示双轴（事件），还有各个按钮，它们对应了各自的事件。称这些为 virtual devices，它们对应各自的事件。Mapper editor 右下部分是一组功能，对应的是十组 DOXBox 功能。

尝试按键盘的按键，比如按下空格键，这是可以看到编辑器中的 virtual keyboard 相应显示空格键的状态改变。这个过程解释为：用户通过键盘输入了一个“Space”，通过默认的映射设置，“Space” => Space，注意后面这个 Space 表示一个事件，就是 mapper editor 界面注意显示的内容，看得见的基本都代表相应的事件（Event）。用户通过硬件输入触发了这些事件，所以产生了相应的结果：这里就是一个空格字符。

现在点击 virtual keyboard 中的空格，可以看得左下角显示其事件名称为 key_space，而当前映射的输入是一个空格按键 (Key Space)：

    EVENT: key_space
    INPUT: Key Space

现在尝试设置通过 Ctrl 来触发空格事件：点击 INPUT 下方的 Add 按钮，这时周围按钮消失，只显示 Add 按钮提示用户通过输入设备指定一个能触发 key_space 这个事件的输入。右侧通过红色字提示：Press a key/joystick button or mve the joystick，告知只能通过键盘或摇杆来触发，不能使用鼠标。然后按下键盘左侧的 Ctrl，完成输入，这时编辑器界面回复原样，但是更新了事件对应的输入：

    INPUT: Key Left Ctrl

表示完成了一个映射关系的添加，然后点击右侧的 Save 按钮就可以保存起来，以后运行 DOSBox 依然有效。这里为空格事件添加了一个输入映射，原有的依然有效，可以通过 Next 按钮枚举这些设置，通过 Del 按钮删除不需要的映射。虽然 Left Ctrl 按键映射到了空格事件，但是原有的映射还有效，所以 Ctrl 按键可以触发 Ctrl+Space 组合键。键盘的 Ctrl、Alt、Shift 三个修饰键对应在 DOSBox 中称为 Mod1、Mod2、Mod3，有左右之分，它们本身就是已经设置好的事件映射。Host 键是一个特殊指定的按键，DOSBox 专门用来执行各种操作，默认的 Host 键对应键盘的 F11 功能键，也一样可以设置一个自己方便使用的按键。这几个键可以设置激活状态，只有满足这些已激活的按键才会触发相应的事件。

在右下部分将功能组切换到第二组，会罗列出 Capture mouse 事件，DOSBox 默认使用 Ctrl+F10 触发鼠标捕捉事件，这时鼠标只能在 DOSBox 中活动。再次按 Ctrl+F10 释放鼠标。可以尝试将其改为 Alt 键触发鼠标捕捉。注意在 mapper editor 中并不会和正常使用中那样触发鼠标捕捉，它只显示按键对应触发的事件（Capture mouse），需要捕捉鼠标，可以点击 Capture 按钮，它就在 Save 按钮的左侧。

Send special key 是个特别功能，默认使用 Host + Del 触发，具体触发的是什么则通过 Main -> Send special key 菜单中勾选。可以通过配置文件 [dosbox] 分类中指定默认的特殊组合键，比如 mapper send key=alttab 用于切换任务。其实这种通过菜单执行的软件设计并不是最有效的命令执行方式，Vim、Emacs、Sublime Text、VS Code 等软件有较深入的探索，无论是命令面板或者命令模式都非常有效率。

DOSBox-X 会将事件报告给 DOS 应用程序，就像正常电脑中使用键盘、鼠标等硬件那样输入，所以，事件 (EVENT) 其实就是虚拟机内部的硬件输入，它只是需要通过绑定 (BIND) 映射关系来让用户方便控制。

最后，总结一下 mapper editor 的功能及核心概念：

• EVENT - 事件代表 DOSBox 虚拟机环境内的软件所接收到的输入：按键、摇杆、鼠标等设备的输入；
• BIND - 将真机中 SDL 图形应用框架获得的由硬件产生的输入与 DOSBox 中的事件映射起来；
• Mod1,2,3 - 修饰键，为某输入设置触发事件要求的修饰状态，默认的修饰设置为：Mod1 = Ctrl, Mod2 = Alt, Mod3 = Shift；
• Add - 为某事件添加新的输入，设置新的映射关系，将物理机器的键盘、摇杆、鼠标等设备产生的输入绑定到某事件；
• Del - 删除某事件现有的绑定关系，每个事件都可以设置多个映射关系，并且硬件的某个输入可以绑定到多个事件；
• Next - 查看某事件的下一个映射关系，配合 Del 可以删除某事件的所以映射关系。

1981-1983 年早期的 MS-DOS 1.x/2.x 单机时代，最初是为 IBM PC 设计的单用户、单任务操作系统，仅支持基本的磁盘管理和命令行操作，完全没有网络功能。MS-DOS 初步支持网络在 1984-1987 年期间，1984 年 发布的 MS-DOS 3.1 是首个支持网络的版本，而且是局域网（LAN， Local Area Network），标志着 DOS 开始具备简单的网络功能。

1995 年发布的 Windows 95 内置了 TCP/IP 协议栈和拨号网络支持，标志着个人电脑开始广泛接入互联网。其内嵌的 MS-DOS 7.0 也支持长文件名和大硬盘，但仍以单机为主。

1996 年发布 Windows NT 4.0，这是一个完全脱离 MS-DOS 的现代操作系统内核，提供现代网络技术支持，包括域管理、远程访问服务（RAS）和更强大的安全功能。Windows 2000/XP 进一步整合了 Active Directory 和 VPN (Virtual Private Network) 支持，而 Windows 10/11 则完全移除了 DOS 底层，专注于云计算和现代网络协议（HTTP/3、Wi-Fi 6）。

1960s-1970s 年代是计算机网络技术萌芽阶段：

• 1961 年，保罗·巴兰（Paul Baran）和唐纳德·戴维斯（Donald Davies）分别提出分组交换（Packet Switching）概念，奠定现代网络基础。
• 1969 年国际互联网的前身 ARPANET 诞生与美国国防部高级研究计划局（ARPA），首个分组交换网络有 4 个节点。
• 1974 年，TCP/IP 协议雏形，文顿·瑟夫（Vint Cerf）和罗伯特·卡恩（Robert Kahn）提出 TCP 协议，后分拆为 IP（网络互联）和 TCP（传输控制）。

1990-1995 年 Windows 3.x 则是发布网络附件版本（Windows for Workgroups，简称 FWG) 支持对等网络（Peer-to-Peer）和 Novell NetWare 客户端，这是微软首次在图形界面中集成网络功能。但是 Windows for Workgroups 3.11 不支持因特网拨号网络模式，它需要安装第三方的软件，而且还常常和系统自身的网络功能冲突。只不过内建 LAN（局域网）的支持对于当时的商业用户来说也是非常重要的需求，Windows 3.1 仅仅支持 Novell Netware 网络，对于商业用户来说，这一点尤为重要，因为那个年代还是以局域网为主，也是 Novell 的天下。还有在这一时期的引入的远程访问服务（Remote Access Service, RAS），标志着微软开始支持远程拨号连接，为企业用户和家庭用户提供了初步的远程联网能力。

1990 年代初，随着企业网络和早期 ARPANET/NSFNET 互联网的发展，用户需要从外部访问公司内部网络。当时的主流远程连接方式是通过调制解调器（Modem） 进行拨号（POTS，Plain Old Telephone Service）。Novell NetWare 和 BBS（电子公告板系统）已支持远程访问，但微软需要自己的解决方案。

1992 发布的 Windows 3.1 本身不内置 RAS，但可通过 Microsoft LAN Manager 或 Windows for Workgroups 3.11（简称 WfW 3.11）扩展支持。WfW 3.11 操作系统与 Windows 3.11 差别在于网络功能，它是首个内置基本网络功能的 Windows 版本，支持对等网络（Peer-to-Peer）和 RAS 客户端功能，需从安装盘加载“Remote Access Service”组件，还要配置 Modem 的 COM 端口和初始化字符串（如 AT&F&C1&D2）。Windows 3.x 的 RAS 是早期远程访问的关键技术，尽管受限于拨号速度和安全性，但它为后来的 Windows 95/NT 远程功能铺平了道路。

Windows 95 内置拨号网络 （Dial-Up Networking, DUN），提供更友好的 RAS 客户端界面，并支持 PPP 协议。仍依赖 Modem，但速度提升至 56 kbps（V.90标准）。

RAS 的核心功能是调制解调器拨号联网：通过标准 AT 命令集建立连接，速度通常为 14.4 kbps 或 28.8 kbps。支持多种网络协议：

• NetBEUI（默认，适用于小型网络）
• IPX/SPX（用于 Novell NetWare 兼容）

RAS 缺点：

• 速度极低：28.8 kbps Modem 的理论速度仅约 3.6 KB/s，实际受线路质量影响更低。
• 单连接：通常仅支持单用户拨入，无法像现代 VPN 那样处理多并发会话。

Windows 3.11 FWG 系统中使用的 NetBEUI（NetBIOS Extended User Interface）是一种网络协议，主要用于小型网络环境中。尽管在现代网络中，TCP/IP 协议更为常见，但 NetBEUI 在某些特定场景下仍有其应用价值。NetBEUI 是 Windows 98 之前的操作系统的缺省协议。NetBEUI 协议是短小精悍、通信效率高的广播型协议，安装后不需要进行设置，特别适合于在“网络邻居”传送数据。NetBEUI 缺乏路由和网络层寻址功能，既是其最大的优点，也是其最大的缺点。因为它不需要附加的网络地址和网络层头尾，所以很快并很有效且适用于只有单个网络或整个环境都桥接起来的小工作组环境。NetBEUI 帧中唯一的地址是数据链路层媒体访问控制（MAC）地址，该地址标识了网卡但没有标识网络。路由器靠网络地址将帧转发到最终目的地，而 NetBEUI 帧完全缺乏该信息。

IBM 于 1985 年提出 NetBEUI 主要用于 20 到 200 台计算机的小型局域网中，比如早期的 DOS、LAN Manager、Windows 3.x 等等。NetBEUI 协议可以看作是 NetBIOS 协议的延伸、改良版本，具有体积小、效率高以及速度快等特点。NetBEUI 可以看作是一种传输协议，而 NetBIOS 仅仅是通过一组命令来让系统使用网络而已。

NetBEUI 本身不能直接连接互联网，因为它是一个非路由协议（仅限本地网络）。要连接互联网，需要额外配置 TCP/IP 协议栈，第三方可用的工具包括 Peter Tattam's Trumpet Winsock（推荐），这是是一个 TCP/IP 协议栈实现，允许 Windows 3.x 通过拨号（PPP/SLIP）或局域网访问互联网。Windows 95 开始原生支持互联网功能，并内置了 Internet Explorer 1.0 浏览器，标志着微软正式将互联网集成到操作系统中。拨号网络（Dial-Up Networking）支持 TCP/IP 协议，但仍需手动配置 PPP 拨号连接。Windows 98 增强了互联网功能，内置 Internet Connection Sharing（ICS）允许共享拨号连接。

Microsoft LAN Manager is a networking system for OS/2 similar to their earlier MS-NET product. Licensed variants of this product include 3Com 3+Open, HP LAN Manager/X, IBM LAN Server, and Tapestry Torus.

Microsoft LAN Manager 2.x 是微软在 1980-1990 年代初推出的基于 OS/2 的网络操作系统（NOS），用于构建企业级局域网（LAN）。它是 MS-NET（1985年）的后续产品，并成为微软早期企业网络解决方案的核心。前身 MS-NET 是微软首个网络操作系统，运行在 MS-DOS 上，提供基本的文件和打印机共享，但性能有限。LAN Manager 最初是为微软和 IBM 联合开发的 OS/2 操作系统设计的，后来 IBM 基于它开发了 IBM LAN Server。当时的主要竞争对手包括 Novell NetWare、Banyan VINES 和 3Com 3+Share。

Windows 3.x/9x 时代，电路硬件水平还不够先进，其中一个突出的问题是中断处理，「中断请求」IRQ（Interrupt Request）是计算机系统中的一种中断机制，允许外部设备或程序通过发送信号来打断 CPU 的正常执行流程，从而引起 CPU 执行特定的中断服务程序（Interrupt Service Routine, ISR）。

Windows 3.x/9x 时代流行的是 ISA总线设计、操作系统调度能力不足 和 硬件生态混乱。随着 PCI/USB 和 APIC 的普及，IRQ 冲突问题在 Windows 2000/XP 后基本解决。

Windows 3.x 混合使用实模式、保护模式，既需要兼容 DOS 实模式驱动，又需要支持 VxD（Virtual Device Driver）虚拟设备驱动程序。导致 IRQ 管理混乱（实模式驱动直接操作硬件，绕过系统调度）。虚拟设备驱动（VxD）虽在保护模式下运行，但仍依赖静态 IRQ 分配，缺乏动态协调能力。

Windows 环境下驱动程序共有三类：

• VxD（Virtual Device Driver，虚拟设备驱动）用于 Windows 3.1/95/98/Me 操作系统中；
• KMD（ Kernel Mode Driver，内核模式驱动）用于 Windows NT；
• WDM（Win32 Driver Mode，WDM 驱动程序模型）起源于 Windows 98 的跨平台的驱动程序模型；

其中 WDM 驱动模型是在 Windows NT 4.0 驱动程序结构上发展起来的，但是它却有了本质上的提高，特别是增加了即插即用 (PnP, Plug and Play)、高级电源管理 (Power Management)、Windows 管理接口 (Windows Management Instrumentation)。更重要的是，WDM 是一种通用的驱动模式，提供了包括 USB、IEEEl394 和 HID 等在内的一系列驱动程序类。

• WDM 驱动程序是分层结构，典型设备驱动被分成：高层、中间层、底层，每层驱动 I/O 套接；
• WDM 引入 FDO（Functional Device Object）与 PDO（Physical Device Object）概念；

这一切高级功能都没有出现在 Windows 3.x 乃至 Windows 95 系统中。PnP 实现不完善，Windows 95 的 PnP 功能孱弱不全，需配合 BIOS PnP 使用，但多数主板 BIOS 支持有限。非 PnP 设备（如旧声卡、网卡）仍需手动配置 IRQ，易引发冲突。系统设计的资源分配算法过于简单，只优先分配空闲 IRQ，但不会智能回收或重新分配已占用的 IRQ。这样的缺失管理的驱动生态反过来作用与设备驱动开发方，导致厂商驱动质量参差不齐，驱动兼容性差，许多驱动未遵循 PnP 规范，强行占用固定 IRQ（如经典声卡默认霸占 IRQ 5 或 7）。还有DOS 程序的干扰：在 Windows 9x 中运行 DOS 游戏时，可能触发实模式驱动，导致 IRQ 被锁定。

上个世纪末（1970s-1980s）正是计算机革命进入个人计算机时代，各种设备爆发式出现，多设备需求爆发，出现了“多媒体电脑”这样新鲜又馋人的概念。1990 年代开始普及 PC 声卡、网卡、SCSI 卡、显卡等，IRQ 需求远超 ISA 总线承载能力。典型多媒体配置案例：光驱（IRQ 15）、声卡（IRQ 5） + 网卡（IRQ 10） + 串口（IRQ 4），配置好常用设备基本仅剩一两个 IRQ 可用。ISA（Industry Standard Architecture）总线仅支持 15 个硬件中断（IRQ 0-15），但实际可用中断仅 8-10 个，因部分 IRQ 被系统固定占用：

SLiRP（Serial Line IP Protocol）是一种在串行线路上封装 IP 数据的协议，常用于拨号上网或模拟网络环境。串行线路（如电话线）传输 IP 数据包，支持动态 IP 分配（需结合 PPP）。SLiRP 无协议类型字段（仅支持 IP）、无校验字段（依赖上层纠错）。PPP 是 SLiRP 的改进版，支持多协议（如 IPX、OSI）、动态 IP 分配和链路层校验。

PCap（Packet Capture）是一种用于网络数据包捕获的文件格式和 API，广泛应用于网络分析工具（如 Wireshark、tcpdump）。Windows 主机上，需要安装 WinPcap（Windows Packet Capture）开源的 Windows 网络数据包捕获库，允许 DOSBox-X 这类应用程序直接访问底层网络流量（绕过 TCP/IP 协议栈）。
PCap 项目现已停止维护（最后一个版本 4.1.3），WinPcap 的继任者 Npcap 由 Nmap 团队开发、维护，目前还在持续更新。WinPcap 是 Windows 网络抓包的基石技术，尽管已被 Npcap 取代，但其设计理念仍影响深远。如需开发抓包工具或分析网络协议，甚至是 DOSBox-X 这样实现网络协议，掌握 WinPcap/Npcap 是必备技能。

Npcap 实现了 Win10 驱动程序，叫做 NPF（Netgroup Packet Filter），该驱动从 Win10 miniport 驱动获取网卡数据实现监控网络数据包的功能（Win10 使用 miniport 驱动控制网卡）。数据流逐级传递：Network -> NPF Driver -> Packet.dll -> wpcap.dll -> Application，这也是 NMap 网络嗅探工具的工作流程。

Windows 系统下构建的 DOSBox-X 可以直接使用内置的 DOS 命令 (DIR, MD, COPY) 通过 UNC〔United Nations Charter〕路径访问网络资源，比如 \\MACHINE\FOLDER，只要网络重定向程序功能没有关闭。

DOSBox-X 模拟的 NE2000 网卡默认使用 IRQ 3 以及 IO 端口范围 300-31F，就如同真实的 NE2000 网卡适配器一样，一些 NE2000 驱动可以检测到它。

****

使用 IRQ 3 的问题就是它与 COM2 串口需要争夺中断资源，在不需要使用 COM2 接口时，这还不算是个问题。特别是在 Windows 95/98/ME 等系统中，经常起冲突，一个解决办法是禁用 COM2 串口，或者给 NE2000 网卡换一个 IRQ，比如 IRQ 10。DOSBox-X 配置文件中记录下 nicirq=10，你需要确保驱动程序正确加载。

****
NOTE: Setting the NE2000 to IRQ 10 is not possible if you’re emulating a 8086 (`machine=8086`), as they only have IRQ 0-7 available. In that case it is probably better to disable COM2.
****

# This setting enables or disables the NE2000 emulation.
ne2000=false
# Valid values: true, false

nicbase=300
# Valid values: 200, 220, 240, 260, 280, 2C0, 300, 320, 340, 360

nicirq=3
# Valid values: 3, 4, 5, 9, 10, 11, 12, 14, 15

# This is the MAC address of the emulated NE2000 adapter.
# Only one instance of a MAC address may exist on a network.
macaddr=AC:DE:48:88:99:AA

DOSBox-X 默认的 IRQ 配置：

• IRQ3 to COM2 serial port (enabled by default in DOSBox-X)
• IRQ4 to COM1 serial port (enabled by default in DOSBox-X)
• IRQ5 *may* be assigned to the sound card (not the case by default in DOSBox-X)
• IRQ9 is an alias from IRQ2 but should be safe to use
• IRQ10 free
• IRQ11 free
• IRQ12 used by the PS/2 mouse emulation
• IRQ14 used by the primary IDE/ATA emulation
• IRQ15 used by the secondary IDE/ATA emulation (usually CD-ROM drive)

****
WARNING: The default IRQ value (3) conflicts with the emulated COM2 port that is enabled by default.
****

****
WARNING: If you’re emulating a 8086 CPU machine type, the valid IRQ needs to be in the range of 0-7, which in this case effectively means 3, 4 or 5. This is because the 8086 only had a single PIC (Programmable Interrupt Controller), while later machines had two.
****

****
WARNING: If you want to run multiple DOSBox-X instances on the same network, you MUST ensure they all have a different MAC address. The first 3 bytes of MAC are known as the OUI (Organisational Unique Identifier), and typically represent the network card manufacturer. The *AC:DE:48* OUI used by default, is a special private range, and it is recommended that you use this range. The last 3 bytes can be freely chosen. Each byte can range from 00 to FF.
****

****
NOTE: There are two different back-ends to the NE2000 adapter emulation, namely pcap and slirp. The default is `backend=auto`, which implies `backend=slirp` if SLiRP support is available, otherwise `backend=pcap` is implied if PCap support is available.
****


PCap 后端方式又称「混杂模式」 "Promiscuous mode"，这可以让 DOSBox-X 中的程序使用多种传统网络协议，包括 IPX/SPX 和 NetBIOS Frames (aka NetBEUI)，以及 TCP/IP，这个模式可以让不同的 DOSBox-X 实例进行同网络通信，还可以让同样使用这些协议的传统 PCs 在统一网络中。通过 PCap 后端提供的底层网络访问，可以绕过宿主系统的 TCP/IP 协议栈，实现网络底层协议的构建。尽管，PCap 后端有如此强大的底层操作能力，但是在某些情况下，这是不可行的：

• Network Adapter or Driver not supporting Promiscuous mode (most wireless adapters fall into this category)
• Your Ethernet switch not allowing multiple MAC addresses on a single port, or doing any kind of MAC address whitelisting.
• Sandboxed versions of DOSBox-X (e.g. Flatpak) not allowing the required low-level access

技术背景：

• 本地回环地址（loopback）用于本地主机使用网络协议进行通信而无需经过网络硬件设备，用于测试本地服务（如 Web 服务器、数据库）是否正常运行，或者实现进程间通信（IPC）。IPv4: 127.0.0.1（最常用），整个 127.0.0.0/8 网段均保留为回环地址。IPv6: ::1（等效于 IPv4 的 127.0.0.1）。
• 以太网数据包 MTU/MRU 参数分别表示
** • 最大接收单元 (Maximum Receive Unit），允许发送至客户机（Guest）的以太网数据包的最大大小。
** • 最大传输单元 (Maximum Transmission Unit),允许从客户机（Guest）发出的以太网数据包的最大允许大小。
• 标准以太网 MTU：1500 字节（含 IP 头和数据负载，不含帧头和尾）。
• 巨型帧（Jumbo Frame）：部分网络支持 MTU=9000，可提升大文件传输效率，但需全网设备兼容。
• libslirp 的限制：作为用户态网络栈，默认采用保守的 1500 字节，避免底层网络兼容性问题。

****
NOTE: If you want to use a larger MTU than default, your hosts network adapter and your network switch needs to support it, otherwise the packets will get truncated.
****

****
NOTE: If you want to use a larger MRU than default, your hosts network adapter and your network switch needs to support it, otherwise the packets will get truncated.
****

MRU 应与 MTU 保持一致，以确保双向通信兼容性，否则可能导致数据包分片或丢弃。若设置为 0，将自动采用 libslirp 默认值 1500 字节（标准以太网帧大小）。不建议超过 9000 字节（巨型帧/Jumbo Frame 的常见上限）。若需调整，建议范围 576–9000（超过 1500 需确保网络设备支持）。

比如 Guest 发送 2000 字节包，但 Host 仅接收 1500 字节，数据包大小不一致会导致单向数据包被丢弃。检测网络支持的 MTU 可以在 Host 系统使用 ping -s <size> -M do <IP> 测试（如 ping -s 1472 -M do 8.8.8.8，其中 1472 + 28 协议头字节 = 1500。

如需自定义值，请在 DOSBox-X 配置文件中明确指定（例如 mru=1492 用于 PPPoE 环境）。

设置网络适配器方式有两种：

• 指定适配器的编号（如 realnic=9）
• 指定适配器名称的部分或完整关键字（如 realnic="Realtek"）

如需在 DOSBox-X 中使用 PCap 功能，请在配置文件中添加以下段落。通常情况下，唯一需要设置的参数就是 realnic。假定主机中有以下网卡设备，那么就可以设置 `realnic=9` 或者 `realnic=Realtek` 都可以，为了有唯一的名称区别，还可以使用完整的设备名称： `realnic="Realtek USB NIC"`。推荐使用设备名，因为网卡序号可能因为系统环境变化而改变，包括需要管理设备的虚拟机的影响。

....
LOG:  9. rpcap://\Device\NPF_{AAAAAAAA-BBBB-CCCC-DDDD-XXXXXXXXXXXX}
    (Network adapter 'Realtek USB NIC' on local host)
....

不同于 PCap 的混杂模式，SLiRP 后端并不要求混杂模式，因此 SLiRP 可以用于无线网卡，并且可以在大多数沙盒环境（sandboxed environments）中工作。当然，SLiRP 也有缺点约束：

• 不是支持所有平台，比如不支持 Windows Visual Studio 构建的版本；
• 只支持 TCP/IP 协议，其它协议如 IPX/SPX 必须封装成 TCP/IP 才能在 DOSBox-X 内运行。
• DOSBox-X 实例将作为一个网络地址转换网关（NAT, Network Address Translation），这意味着：
** • 可主动向外通信（例如下载文件）。
** • 局域网（LAN）内的其他设备无法主动发起新连接到该 DOSBox-X 实例。
** • 同一局域网内两个使用 backend=slirp 的 DOSBox-X 实例无法直接互通。
   但是可以通过 tcp_port_forwards= 和 udp_port_forwards= 选项配置端口转发来绕过此限制。

通常不需要修改前面给出的 SLiRP 配置参考给出的默认值，使用本地的 IP 地址 10.0.2.0/24 (Class 3)，修改 ipv4_host 最后一组数值，就可以得到几百个 IP 地址。

关于端口转发设置，DOSBox-X 安装目录下 dosbox-x.reference.full.conf 有详细说明：udp_port_forwards 和 tcp_port_forwards 端口转发设置格式一样，只是分别对应 TCP/UDP 协议：基本格式有多种，最简单的就是用空格分隔开的一组端口号。比如 21 80 443 表示转发 FTP/HTTP/HTTPS 等协议的端口，相应的网络流量就会通过 NAT 网管流入到 DOSBox-X 内部的 DOS 客户程序中。

[cols="3,2,8"]
|===
|TCP/UDP Port Forwards         |Examples          |Notes

| port1  port2  port3 ...      | 21 80 443        |This which will forward FTP, HTTP, and HTTPS into the DOS guest.
| host:guest  ...,             | 8021:21 8080:80  |This will forward ports 8021 and 8080 to FTP and HTTP in the guest
| start-end ...                | 27910-27960      |This will forward ports 27910 to 27960 into the DOS guest.

NOTE: • If mapped ranges differ, the shorter range is extended to fit. {BR}
      • If conflicting host ports are given, only the first one is setup. {BR}
      • If conflicting guest ports are given, the latter rule takes precedent.
*****

地址掩码（Netmask），又称子网掩码，DOSBox-X 使用 ipv4_netmask 设置地址掩码。虽然看起来和 IP 地址使用一样的四组十进制数值格式表达，但是他们是完全不同的概念。IP 地址包含网络号（Net Number）和主机号（Host Number），并且 IPv4 地址固定为 4 个字节（32bits），根据网络地址分类规范（Class A - C），不同级别的地址使用不同的比特位来表示网络号和主机号。Netmask 就是用来计算 IP 地址边界的一个值：它使用连续的比特 1 表示 IP 地址上对应位置是网络号。比如 255.255.255.0 对应二进制就是连续的 24 个比特都是 1，那么对应 IP 地址的前面三组十进制数就是网络号，而主机号使用一个字节表示，也就是这个网络可以分配的有 256 个 IP 地址，包括特殊用途的广播地址或回环地址等等。

无类别域间路由 CIDR (Classless Inter-Domain Routing) 是一种用于 IPv4 和 IPv6 地址 的表示方法，它允许网络管理员更灵活地分配和路由 IP 地址，并且表达更简洁。比如 IP 127.0.0.1 和掩码 255.255.255.0 这组传统表达方式对应的 CIDR 就是 127.0.0.1/24，一目了然。

IP 协议文档 RFC 791 中将 32-bit 得 IP 地址划分成三个类型：

      High Order Bits   Format                           Class
      ---------------   -------------------------------  -----
            0            7 bits of net, 24 bits of host    A
            10          14 bits of net, 16 bits of host    B
            110         21 bits of net,  8 bits of host    C
            111         escape to extended addressing mode

A 类地址的网络号为 0 ~ 127 (0x00 ~ 0x7F)，主要用于超大型的骨干网络，其中 0.0.0.0 和 127.0.0.0 属于特殊用途的保留地址。B 类地址网络号为 128.000 ~ 191.255 (0x80 0x00 ~ 0xbf 0xff)，总共 stem:[2^{14} = 16384] 个网络。C 类地址网络号是 192.000.000 ~ 255.255.255 总共 stem:[2^{21} = 2097152] 个网络号，这类地址主要用于局域网。

特殊地址范围（RFC 791 补充）

[cols="1,3"]
|===
|地址块         |用途

|0.0.0.0/8     |保留（如 0.0.0.0 表示默认路由）。
|127.0.0.0/8   |回环地址（如 127.0.0.1 用于本地测试）。
|224.0.0.0/4   |D 类（组播地址，如 224.0.0.1 用于本地子网所有主机）。
|240.0.0.0/4   |E 类（保留用于实验）。
|===

注：D 类和 E 类在 RFC 791 中定义，但不属于主分类（A/B/C）。

=== Linux Networking Configuration

🔖 Install libpcap and/or libslirp

[source,bash]
----
# Debian based (e.g. Ubuntu)
sudo apt-get install libpcap libslirp

# Red Hat, SUSE or Fedora
sudo dnf install libpcap libslirp
----

🔖 Check if your DOSBox-X binary supports networking

The provided RPMs have networking enabled, but if you compiled DOSBox-X yourself and the libpcap or libslirp headers where not installed, the resulting DOSBox-X binary will lack libpcap and/or libslirp support. To check if your binary has networking support, run the following command:

[source,bash]
----
$ ldd /usr/bin/dosbox-x |grep "pcap\|slirp"
   libpcap.so.1 => /lib64/libpcap.so.1 (0x00007f7877a7a000)
   libslirp.so.0 => /lib64/libslirp.so.0 (0x00007f7877a5c000)
----

In the above example, the DOSBox-X binary has both libpcap and libslirp support, meaning it has networking. If the command returns nothing you do not have networking. If you’re DOSBox-x binary has no networking, your options are to use the pre-compiled RPM package, or compile it yourself with libpcap and/or libslirp support enabled.

🔖 Setup permissions for PCap

The provided RPM packages automatically set up the necessary permission for libpcap to function.

Otherwise, you need to ensure that the DOSBox-X binary has permission to listen to and generate low level network traffic (promiscuous mode). You can do this as follows:

[source,bash]
----
$ which dosbox-x
/usr/bin/dosbox-x
$ getcap /usr/bin/dosbox-x
$
----

The first command returns the location of the dosbox-x binary (assuming it is in your path), the second command checks its capabilities. In this case getcap does not return anything, meaning it has no special capabilities, which you need to rectify if you want to be able to have PCap networking in DOSBox-X. Run the following command:

[source,bash]
----
$ sudo setcap cap_net_raw+ep /usr/bin/dosbox-x
----

This command will allow the dosbox-x binary to access the network interface in raw mode (pcap), meaning it can see all the traffic on all the network interfaces.

To validate that now the DOSBox-X binary indeed has the cap_net_raw capability, run:

[source,bash]
----
$ getcap /usr/bin/dosbox-x
/usr/bin/dosbox-x = cap_net_raw+ep
----

Warning: If you manually install the dosbox-x binary, you will have to take this step each time you do an upgrade.

🔖 Locate host network interface for PCap

You now need to find which host network interface you want to use for bridging with PCap.

For this you need to have a DOSBox-X config file with NE2000 support enabled, and you need to know which host network adapter will be used for bridging. It is highly recommended to only bridge to wired Ethernet adapters, as wireless adapters generally do not work with PCap.

Create a simple `ne2000.conf` config file as follows:

[source,bash]
----
[ne2000]
ne2000=true
nicirq=10
backend=pcap

[ethernet, pcap]
realnic=list
----

Now, from a terminal, start DOSBox-X, using the ne2000.conf config file you just created.

[source,bash]
----
dosbox-x -conf ne2000.conf
----

Now from the DOSBox-X menu bar, select *Help* followed by *List network interfaces*.

You will now get a list of available network interfaces, similar to the screenshot shown below.

That is an example of the network interfaces that were detected for my Linux PC. Now look at your own list, and locate an appropriate adapter to use. In the above example, 1, or eno1 is the integrated Ethernet of my PC, which we will use in the below example.

Edit the ne2000.conf config file and change realnic= to the number or name of your chosen network interface. e.g.:

[source,bash]
----
[ne2000]
ne2000=true
nicirq=10
backend=pcap

[ethernet, pcap]
realnic=eno1
----

You can merge your config snippet with your Windows for Workgroups, Windows 95 or 98 config file, or use it to run something like mTCP in DOSBox-X.

=== mTCP example

This example uses mTCP to test if networking is working in DOSBox-X.

This requires that you first download the latest version of mTCP, and a NE2000 DOS packet driver (the latter is automatically available in DOSBox-X when the NE2000 networking feature is enabled).

*External links*

* https://www.brutman.com/mTCP/mTCP.html[mTCP homepage]
* http://www.georgpotthast.de/sioux/packet.htm[DOS Packet drivers]

[source,bash]

----

Now in DOSBox-X run the following commands:

[source,bash]
----
MOUNT C mtcp
C:
SET MTCPCFG=C:\SAMPLES\SAMPLE.CFG
NE2000 0x60 10 0x300

----

If all worked fine, you should have gotten an IP address, and you can now do something like

==== Common problem: Invalid MAC Address

When loading the NE2000 DOS Packet driver you get an all FF Ethernet MAC address:

[source,bash]
----
C:\>NE2000 0x60 10 0x300
Packet driver for NE2000, version 11.4.3
Packet driver skeleton copyright 1988-93, Crynwr Software.
This program is freely copyable; source must be available; NO WARRANTY.
See the file COPYING.DOC for details; send FAX to +1-315-268-9201 for a copy.

System: [345]86 processor, ISA bus, Two 8259s
Packet driver software interrupt is 0x60 (96)
Interrupt number 0xA (10)
I/O port 0x300 (768)
My Ethernet address is FF:FF:FF:FF:FF:FF
----

This can actually have several causes.

• Your DOSBox-X binary lacks networking support
• (Linux) Your DOSBox-X binary does not have the right PCap permissions to access networking
• You do not have PCap installed (libpcap on Linux, Npcap on Windows), or SLiRP
• When loading the NE2000 driver you gave the wrong IRQ or IO port.
* This should only affect non-standard setups where you specified a different `nicirq=` or `nicbase=` in your `ne2000.conf` config file.

==== Common problem: Cannot get DHCP lease

When starting DHCP you get only timeouts.

[source,bash]
----
C:\>DHCP
mTCP DHCP Client by M Brutman (mbbrutman@gmail.com) (C)opyright 2008-2020
Version: Mar  7 2020

Timeout per request: 10 seconds, Retry attempts: 3
Sending DHCP requests, Press [ESC] to abort.

DHCP request sent, attempt 1: Timeout
DHCP request sent, attempt 2: Timeout
DHCP request sent, attempt 3: Timeout

Error: Your Ethernet card reported an error for every packet we sent.
Check your cabling and packet driver settings, including the hardware IRQ.
----

This can actually have several causes.

• Check if you got a valid Ethernet MAC address when loading the NE2000 packet driver.
• When using PCap, try to set `REALNIC=` in your `ne2000.conf` config file to a different network interface. In particular wireless adapters are unlikely to work, so try wired Ethernet instead. The order in which the interfaces are listed can also change due to plugging or unplugging devices, or launching certain type of programs like Virtual Machines.
• Perhaps you don’t have a DHCP server on your network, or it is configured to only listen to known MAC addresses. Try to set manual IP settings, suitable for your network, at the bottom of `SAMPLES/SAMPLE.CFG` and try if you can ping.

==== Common problem: Multiple DOSBox-X instances

By default, all DOSBox-X instances use the exact same MAC address (`AC:DE:48:88:99:AA`). If there are multiple DOSBox-X instances running on the same host, or on different hosts on the same network segment, they will conflict with each other.

Unfortunately not all operating systems will warn you about this, but it will cause problems on the network and the DOSBox-X instances will not be able to communicate with each other.

The solution is to define a new MAC address for at least one of the DOSBox-X instances.

In your DOSBox-X config file, in the `[ne2000]` section, add a `macaddr=` line with a new MAC address. The AC:DE:48 range is a reserved range for private use, so just modify the last three number blocks. e.g.,

[source,bash]
----
[ne2000]
ne2000=true
nicirq=10
macaddr=AC:DE:48:88:99:AB

[ethernet, pcap]
realnic=1
----


=== IPX example

There are two ways to enable IPX communication, which was used by some https://www.mobygames.com/attribute/sheet/attributeId,82/p,2/[DOS and Windows games] for multi-player support.

🔖 Using DOSBox-X integrated IPX support

DOSBox-X has integrated support for IPX over IP (IPX encapsulated in IP). You do not even have to enable NE2000 emulation for this.

The advantage of this is that you can communicate with any other system that is directly reachable over TCP/IP. To test this, first `ping` the remote systems from the host OS to ensure connectivity.

A disadvantage of this approach is that you cannot communicate with retro PCs on the same network that are running the native IPX stack.

This process is described on the https://www.dosbox.com/wiki/Connectivity[DOSBox wiki].

🔖 Using the NetWare 16-bit DOS Client

This example uses Novell’ IPX stack, and only works with the PCap back-end. A disadvantage of this approach is that it is not routable over the Internet, meaning it can only communicate with other systems running the native IPX stack on your local network. An advantage is that it can communicate with a real retro DOS PC running IPX on your local network.

This requires that you first download the `vlm121_2.exe` and `vlm121_6.exe` files from the Novell NetWare 16-bit DOS Client. The rest of the NetWare client files are typically not needed for the purpose of running DOS games that require IPX.

*External links*

* http://web.archive.org/web/19961221111819/http://support.novell.com/Ftp/Updates/nwos/vlm121/Date0.html[Novell NetWare DOS/Windows Client v1.21]

Once you have downloaded the files, you need to extract them. The VLM121*.EXE files are individual self-extracting DOS ARJ archives. The easiest way is probably to extract them in DOSBox-X itself.

****
*Notes*

* If you want to do a full installation of the NetWare 16-bit Client, you cannot run the NetWare `INSTALL.EXE` in the emulated DOS environment that DOSBox-X provides. It will fail with "An invalid drive was given in path". You can however install it if you boot a real DOS in DOSBox-X.
* These instructions do not apply to the 32-bit NetWare client (client32) for DOS and 16-bit Windows.
* You can extract the self-extracting EXE files on Linux with the command-line `arj` utility, but you need to use the `-he` switch to disable the Security Envelope check.
****

==== Unpacking the VLM archive in DOSBox-X

Move the files to a temporary directory for extraction, and from that directory launch DOSBox-X.

Then run the following commands:

[source,bash]
----
MOUNT C .
C:
VLM121_2.EXE -y
VLM121_6.EXE -y
----

The files needed are still packed in yet another "Personal NetWare Packed File" archive. Extract them as follows:

[source,bash]
----
MKDIR IPX
NWUNPACK LSL.CO_ \IPX
NWUNPACK IPXODI.CO_ \IPX
NWUNPACK NETBIOS.EX_ \IPX
NWUNPACK DOS\NE2000.CO_ \IPX
EXIT
----

The IPX directory that was created now contains the following files:

* `LSL.COM` (Link Support Layer)
* `IPXODI.COM` (ODI IPX protocol provider)
* `NETBIOS.EXE` (NetBIOS Protocol over IPX)
* `NE2000.COM` (ODI driver for the NE2000 network adapter)


==== Create NET.CFG

Now create a text file called `NET.CFG`, and place it in the same directory as `LSL.COM`, with the following content:

....
Link Driver NE2000
        PORT 300
        IRQ 10
        FRAME Ethernet_802.2
....

*Notes*

* If you used a different IRQ or IO (port) base address, adjust `NET.CFG` accordingly.
* If you’re running on Linux, be sure the `NET.CFG` config file is saved in DOS format (with CRLF line terminators), otherwise the NE2000 driver will not be loaded at the specified resources. If necessary use `unix2dos` to convert it to DOS format.


==== Start IPX

Now modify your `ne2000.conf` config file that you created earlier, such that it contains the following lines in the `[autoexec]` section at the end:

[source,bash]
----
MOUNT C .
C:
IPX\LSL.COM
IPX\NE2000.COM
IPX\IPXODI.COM
----

Adjust paths in the above example as necessary, and you should be able to run it from a command prompt as follows:

[source,bash]
----
dosbox-x -conf ne2000.conf
----

****
NOTE:  NETBIOS], you can also add `IPX\NETBIOS.EXE` at the end. But note that this is NetBIOS *over* IPX, which cannot communicate with other systems running native NetBIOS Frames (NBF) or NetBIOS over TCP/IP.
****

**XMS Memory** +
The eXtended Memory Specification describes ways to access the memory beyond the first MiB in real mode. It is only available to a 286+ CPU. This memory is made available by a DOS real mode driver: HIMEM.SYS.

EMM386.EXE included with MS-DOS 6.x and Microsoft Windows for Workgroups version
3.11 provides support for the Virtual Control Program Interface (VCPI) without
having to set an expanded memory page frame and without having to specify a VCPI
memory pool.

VCPI services are provided by default--no special switches or parameters are
required. If you want to disable VCPI support, you must use the NOVCPI switch on
the EMM386.EXE command line in the CONFIG.SYS file.

Several popular MS-DOS-based applications use DOS extenders to share extended
memory and use of the protected mode of 80386 and higher processors through
VCPI. VCPI is an extension to the expanded memory services (EMS) interface and
is typically implemented by an EMS emulator (such as EMM386.EXE or Quarterdeck's
QEMM386.SYS).

Without VCPI support, "DOS-extended" applications could not run with systems
running in virtual 8086 mode. EMS emulators use virtual 8086 mode to provide
expanded memory mapping and/or create upper memory blocks (UMBs).

To enable VCPI support in the version of EMM386.EXE provided with both MS-DOS 5.0
and Windows 3.1, you must configure EMM386.EXE to emulate EMS. To enable VCPI
without EMS support when the NOEMS switch is active, you must specify a VCPI
memory pool size. For example, if you are using the version of EMM386.EXE from
MS-DOS 5.0 or Windows 3.1, you can use the following command to provide 1
megabyte of VCPI memory:

  DEVICE=EMM386.EXE 1024 NOEMS

The MS-DOS 6.x and Windows for Workgroups version of EMM386.EXE enables VCPI
support without specifying a VCPI size parameter even if the NOEMS switch is
active. Any EMM386 device command that does not include the NOVCPI switch
provides VCPI services.

With EMM386.EXE, VCPI memory is sized using the same parameters as the EMS pool
size (EMM386 [memory] and MIN= parameters).


Include/Exclude Precedence

An X= parameter added to the EMM386.EXE device line is directly adopted by
Windows. Any EMMInclude= or EMMExclude= entry is overridden by any X= parameter
on the EMM386.EXE device line in the CONFIG.SYS file. For example, the following
line in your CONFIG.SYS takes precedence over any conflicting entry:

[source,bash]
----
device=c:\windows\emm386.exe X=C000-CFFF noems
----

When Windows executes, it takes this information before it checks the SYSTEM.INI
file. Even if the SYSTEM.INI file contains a contradictory line, for example:

       EMMInclude=C000-CFFF

Windows keeps the EMM386.EXE parameter.

The same precedence that an EMM386.EXE exclusion takes is true for the I=
(inclusion) parameter.

The D= (DMA buffer size) parameter is not adopted by Windows. If it is necessary
to allocate a larger DMA buffer for EMM386.EXE, it is probably necessary to add
the following to the CONFIG.SYS file. For example, add:

  device=c:\windows\emm386.exe D=96 noems

This would affect anything running under MS-DOS. However, when Windows is
started, the DMA buffer size returns to its default. For the above example, you
should also add the following line to the [386Enh] section of the SYSTEM.INI
file:

  DMABufferSize=96

== Novell NetWare & TCP/IP for Windows 3.11 FWG

Netware 是 NOVELL 公司推出的网络操作系统，Netware 最重要的特征是基于基本模块设计思想的开放式系统结构。这是一个开放的网络服务器平台，可以方便地进行扩充。Netware 系统对不同的工作平台 (D0S、0S/2、Macintosh)，不同的网络协议环境（TCP/IP）以及各种工作站操作系统提供了一致的服务。该系统内可以增加自选的扩充服务(如替补备份、数据库、电子邮件以及记帐等)，这些服务可以取自 Netware 本身，也可取自第三方开发者。

NetWare 客户端服务可以让运行 Windows 的计算机用户通过 NetWare 客户端程序连接到服务器，访问 Novell 目录服务树 (NDS， Novell Directory Services) 及具有平构数据库安全性的服务器上的 NetWare 文件和打印资源。NetWare 客户端服务依赖并利用与 NWLink IPX/SPX/NetBIOS 兼容的传输协议。NWLink 执行网际数据包交换 (IPX)、顺序包交换 (SPX) 以及 NetWare 网络使用的 NetBIOS 传输协议。Microsoft 对这些协议的实现可以无缝地与相同网络适配器上的其他协议共存。

Novell NetWare 早在1980年就被提出，它是建立在施乐网络系统（XNS：Xerox Network Systems）客户－服务器结构的基础上发展起来的。客户机（有时称之为工作站）向服务器发送服务请求，如访问文件和打印机。NetWare 的客户/服务器结构通过远程程序调用支持远程访问服务。当本地客户机程序向远程服务器发送一个调用程序请求时，便开始实现远程程序调用过程，然后服务器执行该远程调用程序，并返回请求信息到本地客户机。

NetWare 4.x 是 Novell 公司推出的网络操作系统（NOS）系列，属于 NetWare 家族的重要版本，主要发布于 1990 年代中期。NetWare 4.x 是企业级目录服务的先驱，其 NDS 设计影响了后来的 Active Directory（AD）。尽管已退出主流，但其高可靠性、低资源占用等特性仍被部分传统系统沿用。

NetWare 4.x 核心特性：

• 引入了革命性的「目录服务」（NDS, Novell Directory Services），采用树状结构（X.500 标准）集中管理用户、组、服务器、打印机等网络资源。支持跨服务器的统一认证和资源访问，取代了旧版（如 NetWare 3.x）的 Bindery（单服务器数据库）。
• 跨平台支持 DOS、Windows、Macintosh、OS/2 和 UNIX 客户端，通过 NetWare Client 软件连接服务器。
• 文件与打印服务，提供高性能的文件共享（基于卷和目录结构）和打印队列管理。
• 安全机制基于 NDS 的权限控制（受托者权限）、文件/目录属性加密，以及用户登录密码保护。
• 内存与磁盘管理以保护模式内核，支持 32 位内存寻址。文件系统（NWFS）支持大容量存储，支持文件压缩、块再分配（Block Suballocation）等优化技术。

NetWare 4.x 的 NDS 技术演变为 eDirectory，后续版本（如 NetWare 5.x/6.x）转向 TCP/IP 并增加对 Linux 的支持。随着 Windows Server 和 Linux 的竞争，NetWare 市场份额逐渐萎缩，最终被 Novell Open Enterprise Server（OES）取代。

Windows 系统需要使用 Novell NetWare 服务就是安装 NetWare 协议驱动程序，提供的协议驱动通常是 "NetWare Client for Windows 3.x" 或 "NetWare DOS/Windows 3.1 Client"，用于在 Windows 3.11 环境下连接 NetWare 服务器。可以在安装包中的 WINDRV 找到驱动程序。

1. 支持的协议

• IPX/SPX：NetWare 3.x/4.x 默认使用 IPX/SPX 协议栈，Windows 3.11 客户端需安装兼容的 IPX 驱动。
• NetWare Core Protocol (NCP)：用于文件共享和打印服务。

2. 驱动文件

• NETX.EXE（DOS 重定向程序，用于 NetWare 3.x 环境）。
• LSL.COM（链路支持层，管理协议栈）。
• IPXODI.COM（IPX 协议驱动）。
• VLM.EXE（用于 NetWare 4.x 及更高版本的客户端）。

3. 安装方式

• DOS 下加载基本网络驱动（如 LSL.COM、IPXODI.COM、NETX.EXE）。
• Windows 3.11 中运行 Setup 程序安装 NetWare Client，选择 Network Setup。
• 添加 Novell NetWare (Workstation Shell 3.x [NETX]) 或 Novell NetWare (Workstation Shell 4.x [VLM])。

VTCP.386 出现在 Microsoft TCP/IP-32 for Windows 3.11 安装包中的原因可能是微软与 Trumpet Winsock 的合作，早期 Windows 3.x 缺乏原生 TCP/IP 支持，Windows 3.11 for Workgroups 最初仅支持 NetBEUI 和 IPX/SPX 协议。微软在 1994 年发布的 TCP/IP-32 补丁包中才正式加入 TCP/IP 支持。微软可能授权或整合了 Trumpet 的代码，在 1990 年代初期，Trumpet Winsock 是当时最成熟的 Winsock 实现之一。微软可能通过合作或授权的方式，将部分 Trumpet 的代码（如 VTCP.386）整合到自己的 TCP/IP 栈中，以加速开发。这只是猜测，不排除有人整合 Peter Tattam 的驱动二次打包后传播。

Windows 3.x 初期缺乏 TCP/IP 支持，1990 年代初期的 Windows 3.1/3.11 网络功能主要依赖 NetBEUI 和 IPX/SPX 协议，官方未提供完整的 TCP/IP 协议栈。用户若需联网（尤其是拨号上网），必须依赖第三方解决方案，如 Trumpet Winsock。微软的 Winsock 1.1 规范是公开的，Trumpet 遵循该标准，因此两者的应用层兼容（如浏览器可通过任一栈联网）。这属于生态适配，而非直接合作。Trumpet Winsock 由澳大利亚开发者 Peter Tattam 开发，成为当时最流行的 Winsock 实现，尤其在拨号（PPP/SLIP）和动态 IP（DHCP）场景中。Windows 3.x 官方长期缺失 TCP/IP 功能，使得 Trumpet 成为事实上的民间标准，直到 Windows 95 发布。微软在 1994 年发布了 TCP/IP-32 for Windows for Workgroups 3.11，首次为 Windows 3.x 提供官方 TCP/IP 支持。但该版本功能有限（如不支持 DHCP），导致许多用户仍依赖 Trumpet。

The OSI Model – The 7 Layers of Networking Explained in Plain English

  • Please        | Physical Layer
  • Do            | Data Link Layer
  • Not           | Network Layer
  • Tell (the)    | Transport Layer
  • Secret        | Session Layer
  • Password (to) | Presentation Layer
  • Anyone        | Application Layer

OSI 开放系统互连七层网络模型中，物理层代表了传输 0 1 比特信号的电路，链路层（Data Link Layer）代表了这些比特数据的链路结构。

网络通信就是把有特定意义的数据通过物理介质传送给对方，单纯的发送 0 和 1 是没有意义的，要传输有意义的数据，就需要以字节为单位对 0 和 1 进行分组，并且要标识好每一组电信号的信息特征，然后按照分组的顺序依次发送。以太网规定一组电信号就是一个数据包，一个数据包被称为一帧（Frame）， 制定这个规则的协议就是以太网协议（Ethernet II、IEEE 802.3 等等）。

一个完整的以太网数据包有三个部分：首部（14 bytes）、数据（46~1500 bytes）和用于校验数据完整性的尾部（4 bytes）。首部固定的 14 个字节包含目标 MAC 地址、源 MAC 地址和类型；数据部分最短为 46 个字节，最长为 1500 个字节，如果需要传输的数据很长，就必须分割成多个帧进行发送；尾部固定为 4 个字节，表示数据帧校验序列，用于确定数据包在传输过程中是否损坏。

以太网规协议定，接入网络的设备都必须安装网络适配器，即网卡， 数据包必须是从一块网卡传送到另一块网卡。而网卡地址就是数据包的发送地址和接收地址，也就是帧首部所包含的 MAC 地址，MAC 地址是每块网卡的身份标识，就如同全球唯一的身份证号码。MAC 地址采用十六进制标识，共 6 个字节， 前三个字节是厂商编号，后三个字节是网卡流水号，例如使用十六进制显示的 4C-0F-6E-12-D2-19。有了 MAC 地址以后，以太网采用广播形式，把数据包发给该子网内所有主机，子网内每台主机在接收到这个包以后，都会读取首部里的目标 MAC 地址，然后和自己的 MAC 地址进行对比，如果相同就做下一步处理，如果不同，就丢弃这个包。

所以链路层的主要工作就是对电信号进行分组并形成具有特定意义的数据帧，然后以广播的形式通过物理介质发送给接收方。在网络的链路上传递数据包会涉及各种问题，以下是其中三个，它们解决方案对应网络层引入的三个协议：

• 发送者如何知道接收者的 MAC 地址？使用 IP 协议携带双方 IP 地址（端口号属于 TCP/UDP 协议）；
• 发送者如何知道接收者和自己同属一个子网？使用 ARP（地址解析协议）：IP 地址映射 MAC 地址。
• 如果接收者和自己不在同一个子网，数据包如何发给对方？路由协议决定数据包传递路径（跨网络通信）。核心问题就是寻路：动态学习并选择最优路径。

应用程序需要互相识别身份，于是传输层协议 TCP/UPD 设计了端口的概念，它们两者数据包一样，都是由首部和数据两部分组成，唯一不同的是，TCP 数据包没有长度限制，理论上可以无限长，但是为了保证网络的效率，通常 TCP 数据包的长度不会超过 IP 数据包的长度，以确保单个 TCP 数据包不必再分割。但是主要功能差别在于 TCP 有可靠性保证机制，确保对方成功接收数据，否则重复发送。

利用传输层协议可以做很多事情了，但是在某些使用场合中，二进制的数据并不是很方便。于是在应用层上设计了 HTTP、FTP、SMTP 等等文本协议，其中 HTTP 是一种比较常用的应用层协议，主要用于 B/S 架构之间的数据通信。

OSI 七层模型对编程应用来说太繁琐，实践中用 TCP/IP 四层模型简化表达，也就是以上主要内容：

• 链路层：对 0 1 比特数据进行分组，定义数据帧，确认主机的物理地址，传输数据；
• 网络层：定义 IP 地址用于定位主机，并通过 IP 进行 MAC 寻址，对外网数据包进行路由转发；
• 传输层：定义端口（TCP/UDP），确认主机上应用程序的身份，并将数据包交给对应的应用程序；
• 应用层：定义数据格式（FTP/HTTP 等等），并按照对应的格式解读数据。


Windows 系统上实现自己的 TCP/IP 协议栈是一项复杂的任务，通常用于研究、网络设备开发或特殊场景（如绕过操作系统协议栈）。可选择实现方式：用户态实现（较简单）或者内核态实现（高性能）。

用户态程序只需要通过原始套接字（Raw Socket）或 WinPcap/Libpcap 捕获和发送数据包。无需内核驱动，调试方便。缺点是性能低，无法完全绕过系统协议栈。Raw Socket：socket(AF_INET, SOCK_RAW, IPPROTO_RAW) 需管理员权限。WinPcap/Npcap 则是捕获链路层数据包，比如 Ethernet 帧。

内核态实现通过 NDIS（Network Driver Interface Specification）或 WFP（Windows Filtering Platform）直接处理网络流量。拥有极高性能，可完全绕过系统协议栈。但是对于个人项目，缺点明显，开发复杂，需驱动签名。

内核开发协议栈的关键组件：

• NDIS Miniport 驱动：处理底层网卡数据。
• NDIS Lightweight Filter (LWF)：过滤/修改数据包。
• WFP：高级流量拦截（但依赖系统协议栈）。

参考书：Windows Network Programming by Len Bass. Developing Drivers with WDF by Penny Orwick.

Windows 1.0 is the first major release of Microsoft Windows, which was released to manufacturing on 20 November 1985 in the United States, and later internationally in May 1986. It is a graphical shell that runs on top of MS-DOS and provides a cooperative multitasking environment that can run applications specifically targeting Windows itself as well as a subset of compatible MS-DOS applications. Aside from being available as a full user environment, it also exists in a runtime variant that developers could ship with their applications. Despite lukewarm contemporary reviews, it enjoyed moderate success and was eventually succeeded by Windows 2.0 in 1987.

The environment consists of three major components: the Kernel (KERNEL.EXE), which provides base services such as the New Executable loader and process management, memory management, and cooperative multitasking; the Graphical Device Interface (GDI.EXE), which provides a device-independent interface to draw graphics onto the screen; and User (USER.EXE), which implements the actual user interface on top of GDI. This base structure was kept intact by later versions of Windows and eventually also carried over to Win32.

Unlike any later releases, Windows 1.0 primarily manages windows by tiling them rather by stacking. This was a design choice promoted by former Xerox PARC employees, which was backed by their research done during PARC's Cedar project, rather than a legal or implementation limitation. In fact, Windows 1.0 supports and internally uses overlapping windows, although this ability is limited to popup windows and certain controls such as menus and dropdowns—by default, windows are tiled on top of an overlapping window manager.

Windows 3.11 是纯 16 位系统，而现代 CPU 是 64 位架构（x86-64）。虽然 CPU 支持 实模式（Real Mode） 和 虚拟 8086 模式 运行 16 位代码，但需要通过复杂的指令转换层，效率极低。Windows 3.11 设计时针对的是 几十 MHz 的 486/Pentium CPU，而现代 CPU 主频高达 GHz 级别。某些依赖定时器的旧程序（如游戏、多媒体应用）会因时钟速度过快而崩溃或运行异常。Windows 3.11 依赖实模式内存模型（最大 16MB 可用，常规内存仅 640KB），而现代系统以 GB 为单位分配内存。现代 SSD 的响应速度远超 1990 年代的机械硬盘，但 Windows 3.11 的磁盘缓存机制（如 SMARTDRV）无法有效利用高速存储，反而可能因 I/O 调度不匹配导致延迟。物理机复古硬件配置：486DX4/100MHz + 32MB RAM + Trident 9440 显卡 + IDE 硬盘。Windows 3.11（原始硬件）启动时间 10-20 秒，使用现代虚拟机可减少至 5-10 秒，虚拟磁盘 I/O 虽然快但无优化。

Intel 386 是一款革命性 32-bit CPU，其强大之处在于分页式 MMU - Memory Management Unit 内存管理单元的出现，使得现代操作系统可以使用内存分页机制（pagination MMU）来管理内存，将真实的内存物理地址保护了起来。早期，80286 之前的系统只能使用分段管理内存（segmented MMU），应用程序可以到处写内存中的数据。程序可访问整个物理地址空间（如 8086 的 1MB 空间），仅少量 ROM 区域受保护。程序可随意读写任意内存这种无隔离的操作给内存管理带来极大的问题，非常容易导致系统崩溃。早期 CPU 可访问的内存地址空间极小（如 8086 的 20 位地址总线），多任务管理几乎不可能。80286 的分段内存管理（Segmented MMU）引入保护模式，支持 16MB 物理内存（24 位地址总线）。通过段描述符表（GDT/LDT）实现内存隔离和权限控制。OS/2 1.x 系统利用 80286 MMU 提供多任务和内存保护，优于 MS-DOS 的实模式。缺陷是分段机制复杂：程序员需手动管理段寄存器（如 DS:SI），易出错。分段地址计算繁琐：逻辑地址 = 段基址 << 4 + 偏移量，效率低下。

image::https://www.xtof.info/386_i386Architecture.png[]
Internal architecture of the 386: the two almost independent MMU units are apparent

Intel 80386 分页机制（Paged MMU）的现代方案则解决了这些历史问题，其核心思想是将虚拟地址空间划分为固定大小的页（如 4KB），通过页表映射到物理内存。页表项（PTE）：存储物理页号、权限位（读/写/执行）、缓存策略等。TLB（Translation Lookaside Buffer）缓存近期访问的页表项，加速地址转换。若 TLB 未命中（TLB Miss），需从内存加载页表，开销较大。分页机制简化了编程，程序使用连续虚拟地址，无需关心物理内存碎片。还能支持多任务，每个进程有独立页表，实现内存隔离（如 Linux 的 mm_struct）。

Linux 采用四级页表（PGD → PUD → PMD → PTE），支持大页（Huge Pages）减少 TLB 压力。系统调用 mmap() 直接操作页表，实现内存动态映射。Intel/AMD CPU 的 NX Bit（禁止执行位）配合分页机制，防御缓冲区溢出攻击。

Early programs could see the whole address space of the machine. It was manageable as it was a tiny space. Programs could also write anywhere, except on a small ROM area hosting the few functions provided by the (primitive) “system”. But as the address space became bigger and the underlying systems evolved, many programs could run simultaneously.

The 80286 came with a feature-rich segmented MMU, allowing a much more complex memory management than the 8086 and able to access up to 16MiB of memory. OS2 1.x, intended to be the successor of MS-DOS on PCs, made good use of this MMU to provide a more modern experience.

But as PC programmers knew very well, segmented memory has limitations and can be a pain to manage. So other memory management schemes were devised.

A more modern way to design a MMU is around pagination. The MMU divides the virtual address space into pages of fixed sizes. When a program accesses a location inside a page, the MMU reads a page descriptor that contains all the information required to do the translation to the physical address. This page descriptor is usually also located in memory, so in order to stay fast enough, paged based MMU have a small cache, the TLB, containing the last descriptors that were accessed. In most cases, it is enough to keep excellent performances.

== Windows NT 3.51
• https://winworldpc.com/product/windows-nt-3x/351[Windows NT 3.x]

Windows NT 3.51 是 Windows NT 线路上一个关键且成熟的版本。它巩固了 NT 内核的稳定性和核心特性（安全性、多任务、多用户、多平台、SMP），完善了 Win32 API 支持，为企业级计算和服务器应用提供了坚实的平台。虽然它的用户界面与同时代的 Windows 95 相比显得过时，但其强大的底层架构为微软未来二十多年操作系统的成功奠定了不可撼动的基础。它是现代 Windows（从 Windows 2000/XP 至今）的直系祖先。

Windows NT 3.1 was the first of the Windows NT series. Sporting the same face as its consumer counterpart Windows 3.1, it was completely different under the hood. A true 32-bit native operating system, Windows NT descended from the work Microsoft did while collaborating with IBM on OS/2 after the great split, and bringing in former DEC employees like Dave Cutler, bringing a VMS influence into the system. It was followed up by Windows NT 4.0.

Windows NT 3.51 可以运行绝大多数 16 位的 Windows 3.1 应用程序，基于 WoW - Windows on Windows 兼容层子系统实现。Windows 10 上直接运行 Windows NT 3.51 的原生 32 位（Win32）应用程序存在兼容性挑战，但部分程序仍可通过特定方式运行。Windows NT 3.51 的 Win32 API 是早期版本，与现代 Windows 10 的 API 存在显著差异（如函数弃用、参数变化）。Windows NT 3.51 程序通常编译为 32 位（x86），而现代 Windows 10 仍支持 32 位应用（WoW64 子系统），但依赖的库可能已失效。Windows 10 已完全移除 16 位支持（NTVDM 子系统），不能运行 Windows 3.x 的程序。

NT 3.51 使用 WoW (Windows on Windows) 的兼容性子系统来运行 16 位的 Windows 3.x 应用程序。WOW 本质上创建了一个虚拟的 16 位 Windows 3.1 环境（一个 NTVDM - NT Virtual DOS Machine 的扩展），在这个沙盒环境中运行 16 位程序。对于标准的、使用官方 Windows 3.1 API 开发的商业软件和实用程序，兼容性通常非常好。像 Microsoft Office 4.x、CorelDRAW! 5/6、Adobe Photoshop 3.0 等流行软件都能正常运行。稳定性优势，由于 WoW 将 16 位应用程序运行在独立的、受保护的虚拟机上，一个 16 位程序的崩溃通常不会导致整个 NT 系统崩溃（这与 Windows 3.1 或 Windows 95/98/Me 不同），大大提高了系统的整体稳定性。

WoW 子系统的限制和缺点：

• 单线程调度： 最重大的限制！ 在 NT 3.51 的 WoW 层中，所有的 16 位 Windows 应用程序共享同一个线程。这意味着：
• 协作式多任务： 这些 16 位程序之间仍然是协作式多任务（就像在真正的 Windows 3.1 上一样），而不是 NT 本身的抢占式多任务。
• 性能开销： WoW 层会引入一定的性能开销，运行 16 位程序通常比在原生 Windows 3.1 或 Windows 95 上稍慢一些。
• 一个挂，全挂： 如果一个 16 位程序进入死循环、挂起或没有正常交出控制权，它会阻塞整个 WoW 会话中所有运行中的 16 位程序。
• 直接硬件访问： NT 严格禁止应用程序直接访问硬件（这是其稳定性和安全性的基石）。任何依赖于直接操作硬件（如特定声卡、显卡或端口）的 Windows 3.1 程序（特别是一些老游戏、多媒体软件、低级工具）很可能无法正常工作或完全无法运行。它们会因权限不足而失败。

DOS 扩展器： 一些 Windows 3.1 程序（尤其是游戏）使用 DOS 扩展器（如 DOS/4GW）来突破 DOS 的 640KB 内存限制并在保护模式下运行。虽然 NTVDM 能运行纯 DOS 程序，但 DOS 扩展器与 WoW 层的兼容性可能存在问题，导致这些程序无法启动或运行不稳定。

特定 API 或驱动程序： 使用了某些非常底层或非标准 Windows 3.1 API 调用的程序，或者依赖特定 VxD (Virtual Device Driver) 的程序（这在 Windows 3.1 中很常见），在 NT 环境下可能找不到所需的驱动或接口，导致失败。

总结：

能运行吗？ 是的，对于标准的、不依赖直接硬件访问的 Windows 3.1 商业和生产力应用程序，NT 3.51 通常可以很好地运行它们，并通过 WoW 层提供了更好的崩溃隔离。

完美吗？ 不完美。存在性能开销、共享线程导致的一个挂全挂问题，并且严重依赖直接硬件访问或特定 VxD 的程序（尤其是老游戏和多媒体应用）很可能失败。

与 Windows 95 对比： Windows 95 本身是 16/32 位混合内核，它对 16 位程序的兼容性通常更“原生”，能更好地支持那些依赖硬件或 VxD 的老程序（虽然稳定性因此较差）。NT 3.51 的优势在于运行 32 位程序和作为服务器/工作站的稳定性。

因此，如果你需要在 NT 3.51 上运行某个特定的 Windows 3.1 程序，最好实际测试一下。对于标准办公软件通常没问题，但对于老游戏或需要硬件加速的程序，则要做好无法运行的准备。

== A visual history of Visual C++

[source,bash]
pandoc -tasciidoc -rhtml http://www.malsmith.net/blog/visual-c-visual-history/

_04 Mar 2017_

Visual {CPP} was Microsoft's implementation of a professional
Windows hosted IDE for developing Windows software. From humble
beginnings, it's grown into a very versatile, popular, and powerful
tool. I used every version of Visual {CPP} since 1.0, and
thought I'd collect some Visual {CPP} screenshots and comments
on these versions.

=== Visual C++ 1.x

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc1.png[msvc1]

[cols=",,",options="header",]
|===
|                  |Visual C++ 1.0/1.5 (16-bit) |Visual C++ 1.1 (32-bit)
|Minimum host OS   |Windows 3.1                 |Windows NT 3.1  
|Minimum target OS |Windows 3.1                 |Windows NT 3.1/Win32s 1.1

|CRT DLL           |N/A                         |MSVCRT10.DLL
|===

Visual {CPP} 1.0 was the first release of Visual {CPP},
released in 1993 for 16 bit development. Version 1.5 was released later
as a 16 bit development tool, and there was also a Visual {CPP}
1.1 for 32 bit development, pictured above. These represented
Microsoft's first major push into a Windows based IDE for {CPP}
development. Prior to IDEs, Windows development was mainly done with
command line compilers and a developer's editor of choice, coupled with
a Windows SDK that provided tools for Windows specific problems.

My first experience with these versions was fairly bad: the Windows
specific tools were still seperate from the IDE, so the IDE itself
represented a Windows editor, and the system required a fair mount of
RAM compared to a DOS based solution so performance wasn't great. The
main advantage of Visual {CPP} as opposed to earlier tools is an
integrated debugger, which particularly in 16 bit Windows, was a huge
advance. Note that 16 bit Windows is a cooperatively multitasked system,
so a process cannot be "stopped" to debug it or the system will hang;
previous debuggers relied on stopping and debugging all of Windows.
Visual {CPP} would emulate the behavior of a stopped process
without actually stopping it, giving the appearance of interactive
debugging.

In 32 bit land the world was very different. Visual {CPP} 1.1
shipped with tools that contained useful bug fixes over the original NT
SDK, but the two were very similar. Because NT had a debugging model for
processes that was designed, and the SDK shipped with an interactive
debugger, the advantages of Visual {CPP} in 32 bit land was more
limited.

16 bit Windows had a very different model to 32 bit Windows with C
runtime libraries. Because each process could determine its own memory
model and floating point behavior, C runtime libraries were always
statically linked into the application. In 32 bit Windows, however, the
option of a dynamically linked CRT was created and Visual {CPP}
1.1 used MSVCRT10.DLL. This choice was a little frustrating for me,
since the NT SDK used CRTDLL.DLL which was included with the operating
system, whereas MSVCRT10.DLL was not, leaving the developer choosing
between buggy tools with simple deployment and fixed tools with painful
deployment.

=== Visual C++ 2

Visual {CPP} 2 was exclusively a 32 bit release in 1994. This
screenshot, which focuses on the editor, does not do justice to how
radical this release really was. Most of the Windows SDK tools are now
integrated, so editing dialog boxes, menus etc are all built in to the
IDE. The CRT DLL was bundled with future OS releases, including Windows
95, and this release was the last release before Windows 95 shipped so a
lot of 32 bit software was written with it. There were 3 releases - 2.0,
2.1, and 2.2. Although I never used anything except 2.0, it's my
understanding that the main enhancements focused on updating the SDK in
preparation for NT 3.51 and Windows 95.

Visual {CPP} 4 was the first "designed for Windows 95" release,
which updated the SDK and UI to conform to Windows 95 guidelines.
Frustratingly for developers though, the CRT DLL didn't ship in the
first version of Windows 95, so despite the UI look and feel deployment
remained a challenge. There were also three releases - 4.0, 4.1, and
4.2. The screenshot above is from 4.1, but aside from SDK changes the
differences are minor.

The other major change in this release was integration of the
help/documentation system into the IDE rather than relying on WinHlp and
other external tools.

One subtle change that happened at this time was seperating Visual
{CPP} between two editions, a standard and professional version.
The important difference is that the standard edition does not have an
optimizing compiler. As a matter of pre-history, QuickC did not have an
optimizing compiler either, so in many ways this was restoring to a
traditional dichotomy. However, the practical effect was that people who
had the standard edition were not aware the functionality was missing
and the result could be some fairly inefficient code for the unwary.

This is also the only Visual {CPP} IDE I spent any serious time
using.

=== Visual C++ 5

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc5.png[msvc5]

[cols=",",]
|===
|Minimum host OS version   |Windows NT 4.0/Windows 95
|Minimum target OS version |Windows NT 3.51/Windows 95
|CRT DLL                   |MSVCRT.DLL
|===

The Visual {CPP} UI was updated to more closely resemble the IE
3/Office 97 UI of its day. Toolbars had double ridge grips and
seperators, with mouseover highlights. Functionally though, the UI
differences seem minor.

Under the covers though, the switch to MSVCRT.DLL was significant. The
intention was to bundle this with the operating system and ensure
applications could (eventually) stop distributing it. In the short term
this created a challenge, because Windows 95 and Windows NT 4 didn't
have this DLL, but in the long term this went according to plan -
Windows 98 and Windows 2000 did ship with it, so over time the need to
distribute the DLL went away.

Particularly as the DLL deployment rolled out, Visual {CPP} 5
was nice for generating compact binaries by default. 
It also included the first version of NMAKE that could pass all 
objects needing building to a single compiler process,
which allowed clmp to function.

=== Visual C++ 6

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc6.png[msvc6]

Visual {CPP} 6 was a small update to Visual {CPP} 5 in
terms of both UI and functionality. The biggest change that I observed
was having an install time check for Internet Explorer 4 and moving the
documentation system to HTML Help. This check was looking at the
registry only however, and the HTML Help system worked (albeit without
perfect CSS formatting) with Internet Explorer 3.

Under the covers, the dependency on Internet Explorer 4 was also
problematic. By default the headers would use new structures that are
only supported when Internet Explorer 4 was present, so unless a
developer consciously set values like `_WIN32_IE` themselves,
programs generated tended to have an IE4 dependency.

One of the things that made Visual {CPP} 6 so long lived is it
was possible to use an updated Windows SDK, up to Windows 2003 Service
Pack 1. This meant that a developer could use Visual {CPP} 6
without sacrificing any operating system functionality, while retaining
the benefit of using MSVCRT.DLL.

=== Visual C++ 2003

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc2003.png[msvc2003]

Visual {CPP} .NET 2003 was the next release I really used. There
was an earlier, very similar release, Visual {CPP} .NET 2002.
The main difference between the two, for native code developers, is that
2002 supported NT 4 as a host system whereas 2003 required Windows 2000.
The UI was radically updated, but I spent so little time using it that I
can't really analyze it intelligently. The change to the CRT DLL meant
that it was not loaded on any released version of Windows at the time,
whereas MSVCRT.DLL was almost ubiquitous by this point, so there was no
incentive to use 2003 as opposed to Visual {CPP} 6 with a newer
SDK.

Shortly after this, the Visual {CPP} toolkit was released, which
was a freely downloadable form of the same compiler, with optimization
support. This marked the first step towards eliminating the crippled
standard edition.

=== Visual C++ 2005

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc2005.png[msvc2005]

|===

|CRT DLL                   |MSVCR80.DLL

Visual {CPP} 2005 revisited the UI once more to make it more
consistent with the Office 2003/.NET 2.0 UI.

Under the covers, this finished the work of retiring the crippled
standard edition of the compiler. Although it was available in multiple
editions, all included and optimizing compiler, so for native code
developers not depending on extra libraries and tools the editions are
interchangable.

The CRT DLL was marked to run on Windows NT 4 but the developers had
clearly not read the fine print on MSDN, which indicated that
GetLongPathName is only available via a statically linked library and is
not in the base system. This means that the CRT DLL won't load on NT 4
out of the box, and getting the compiler to generate NT 4 binaries
requires statically linking the CRT. It's also possible to generate a
"fixed" CRT DLL for NT 4 since source code for the CRT was available,
but great care should be taken to not install that CRT on a system that
should have the real CRT instead.

=== Visual C++ 2008

2005. I always laughed a bit seeing the "9" in the icon, being a simple
visual indicator that it's different in some trivial way.

The more substantial change was updating the CRT to depend on Windows
XP. Windows 2000 support could be retained by not using the DLL. At the
time I was a Windows 2000 user, so this release didn't get much use.

Another seemingly unnoticed detail is that this compiler was the first
to document and fully support multi process compilation, which is
necessary to exploit modern hardware to improve compile times. For older
compilers, there's always clmp.

=== Visual C++ 2012

image:http://www.malsmith.net/blog/visual-c-visual-history/msvc2012.png[msvc2012]

Visual {CPP} 2012 was the release that coincided with support
for Windows 8 development. It included the menu bars that SHOUT AT YOU
BECAUSE THEY CAN, and updated the minimum host OS version to Windows 7.
When it was released, this compiler did not support targeting XP, a
decision that was hastily reversed in the first update. I've always been
a little curious about this - who really wants to target a 2001
operating system with a 2012 compiler? And were so determined to move
from 2010 to 2012 while targeting 2001 that they forced support to be
added? Although this situation seems a little comical outwardly, XP
support has been retained ever since.

=== ...and onwards

As of this writing, Visual {CPP} 2013 and 2015 are released and
2017 is in RC. Visually these come with different themes but are still
visually similar to 2012. The main enhancements are in {CPP}
support (which I don't use), so my only encounters with them is to
validate that they can compile my code, in case somebody else wants to
do that. I have no good reason to use them just yet. Maybe one will
emerge - the one theme running through this list right from the start is
that each release wasn't that useful on its release day but became much
more useful later, once CRT DLLs were deployed, older operating systems
retired, and hardware had advanced.

Microsoft Bookshelf 安装后提供了 msl.exe 阅读器，这是一个常驻内存的程序（Resident Programs），可以配合 Lotus Works 1.00 等字符处理软件使用。因为 DOS 不是多任务系统，只能运行一个任务，T.S.R. (Terminate and Stay Resident) 常驻程序是一种模拟多任务的折中方法。本质上 TSR 程序就是共享同一内存空间的代码片段，和操作系统运行的独享独立内存空间的进程不同，共享内存空间中只有有一方代码出现问题都会导致其它程序运行出错。运行这个驻留程序时 (MSL.EXE /T)，它会短暂出现一个 splash 信息窗，然后隐退，并且给出提示，按键 Alt+Shift 用于弹出手册面板，内容如下。快捷键可能以系统输入法有冲突，可以通过 Options 修改，或者在系统的「高级键盘 -> 更改按键顺序」进行调整。热键冲突会导致 MSL 接收不到按键信息，可以通过多按一个键来避免触发系统热键，而这个组合键将会得到 MSL 的响应，比如 Alt+Shift+S，MSL 会忽略掉多来的按键。

Wordpad 文档本身是文本格式，只不过使用可以嵌套的 {} 花括号为文档的定义格式化规则。类似于 LaTeX 文档结构的设计，但是 LaTeX 使用的“流水式”指令随用随清理，不像 RTF 这种地狱式嵌套的花括号，只要有一个花括号出现问题，整个文档结构都被破坏。RTF（Rich Text Format）使用单引号（'） 作为转义符号，以允许在文档中插入非 ASCII 字符（如 Unicode 字符）。比如使用文档原文本中使用 What\'92s 表示 What’s。但是 Wordpad 打开文档时又不提供编码方案选择，又不能自动正确处理编码，导致文档打开后经常出现乱码。然后再编辑保存，就会喜获乱码损失三部曲。UTF8 编码的 RTF 文件在中文 Winows 系统中打开时一定会发生以下这种情况，使用 GBK 编码保存的文件只是出现的乱码内容不同。可以使用文本编辑器，将转义的 \`92 替换为 \rquote（注意要用空格与内容隔开）。或者使用 Unicode 转义编码，\'92 替代为 \u8217?（包括这个问号）。Windows-1252 转码只支持 2 位十六进制数字。总之，RTF 是一种技术性缺陷严重的文档格式。可以使用 pandoc.org 提供的开源工具进行格式转换。

Wordpad 默认使用系统 ANSI 编码，如果是中文 Windows 则实际是 GB2312/GBK，但若文件实际为 UTF-8或Unicode，则可能乱码。即使是 GBK 编码或者 ANSI 编码，如果使用转义符号也会在中文 Windows 系统导致乱码，因为 \'92 （十六进制）对应的二进制值的最高位是 1（0b10010010），这在中文 GBK 编码中属于中文字符编码的一个字节，因此导致下一个 ANSI 字符也被当作前一个中文字符的第二个字节处理，从而乱码。

Wordpad 在中文 Windows 系统下乱码现象主要是转义字符出现乱码问题。虽然可以使用文本编辑器改写 RTF 文件开头的编码方案，但是这个操作改变不了 RTF 格式的设计缺陷，这种乱码必然会出现，包括 WinHelp 程序中也一样可以中文 Windows 系统中看到普遍的乱码内容。

[source,bash]
----
{\rtf1\ansi\ansicpg936\deff0{\fonttbl{\f0\fnil SimSun;}}

{\rtf1\ansi\deff5{\fonttbl{\f0\fswiss Helv;}...
----

WordPad（写字板）处理包含转义字符的文本时出现乱码，通常是由于编码解析错误或转义字符冲突导致。解决方法参考：修改系统区域设置为中文(简体，中国)之外的语言，或者替代 RTF 中引起转码乱码内容，直接使用相应的中文符号替代，使用 \\'[a-f0-9]{2} 正则去搜索全部转义符号。

RTF（Rich Text Format）嵌入图像时，图像数据会被转换为十六进制编码或二进制格式，并附带控制指令来定义图像属性和位置。RTF 通过 \pict 指令嵌入图像，通用结构如下：

[source]
----
{\pict\<format>\<width>\<height> <image_data>}
----

• \<format>：图像格式标识（如 \pngblip、\jpegblip）。
• \<width>/\<height>：以 缇（twips） 为单位（1 twip = 1/1440 英寸）。
• <image_data>：图像的十六进制或二进制数据。

一、文本处理机制
分块存储与索引定位

文本内容按字母索引表（EAABBCCDD...）分块存储，每块对应特定字母范围（如AA块、BB块），便于快速检索编程术语16。

每个文本块关联坐标元数据（如偏移量、长度），通过预计算的矩形区域（x,y,width,height）定位渲染位置，支持图形化界面显示18。

动态文本渲染

使用 IBM CP437 编码（常见于MS-DOS）处理高位字节（0xC0-0xFF），将二进制数据转换为绘图字符（如边框─、表格╥），实现命令行环境下的图形界面110。

通过缩放因子（_vR）动态调整文本坐标和尺寸，适配不同分辨率设备1。

控制符分隔

高频控制字符（如0x1E记录分隔符、0x0B垂直制表符）标记文本段落边界，实现分页与结构化存储17。

文本块结构示例（基于十六进制数据）
偏移地址	内容	功能
0x000000C0	EAABBCCDD...	字母索引表（A-Z分段）
0x000000E0	Q4406SR7	内部版本号元数据
0x00000100	CF C4 DD D2...	CP437 编码文本（高位字节）
0x00000200	737A 426C 664E...	结构化数据块（API关键词）



技术验证建议使用 CP437 解释文件数据：

[source,python]
with open("file.bin", "rb") as f:
    data = f.read()
    decoded = data.decode("cp437", errors="replace")  # 还原文本界面布局

• 查找 0x1E（记录分隔符）之间的内容，提取独立条目。
• 定位重复字节对（如 AA, BB）后的数据，验证索引逻辑。

=== VIDEO DISPLAY NOTES

To correctly use a Hercules graphics adapter with Microsoft Word and
Programmer's Library, the environment variable HERCGB102 must be set
to TRUE.  Place the following entry in your AUTOEXEC.BAT file:

           SET HERCGB102 = TRUE 

If you have a Hercules graphics adapter and you use Microsoft Word, you
must use Word in character mode (all versions) if you intend to use
Programmer's Library.

If you are using a monochrome monitor driven by a graphics video card, or
a gas plasma display, start Programmer's Library using the /b command line
switch.

Programmer's Library uses the current video page to display data.
Occasionally, less well-behaved software will not inform the bios of what
video page it is using.  This may cause a conflict with Programmer's
Library, and Programmer's Library may appear not to be working.  If this
is true with your software, please check the manual for instruction on how
to make the first video page (page 0) the default.

If you have any difficulty using Programmer's Library in 43- or 50-line
video modes, run the 43.COM program in the CD-ROM's \MSLIB directory be-
fore popping up Programmer's Library.

mouse cursor will be "unfrozen," and the Programmer's Library mouse cursor
will disappear.

=== USING PROGRAMMER'S LIBRARY WITH MULTIPLE CD-ROM DRIVES

Programmer's Library setup creates a file called MSL.INI.  This file
contains paths for each Microsoft Library product.  The paths assume that
each product is in the same logical disk drive as it was when you first
ran setup.

If you change the drive in which Microsoft Library products are found,
you must also change the appropriate path names in MSL.INI.


=== MANUAL SETUP PROCEDURES

If you encounter problems with the setup program or if you simply prefer
to set up manually, follow the procedures below, which assume the
following about your system configuration:

        Hard Drive is drive C:
        CD-ROM Drive is drive D:

  1. On your hard drive, create a subdirectory called "MSLIB".

                C:\>md MSLIB <Enter>

  2. Change to the MSLIB subdirectory by typing "cd MSLIB" and ENTER.

                C:\>cd MSLIB <Enter>

  3. Place the Programmer's Library CD-ROM disc in your D: drive.

  4. Copy all files in the MSLIB directory on drive D: (your CD-ROM
     drive) to the MSLIB directory on drive C.

                C:\MSLIB>copy d:\MSLIB\*.* <Enter>

  5. With your text editor, create an ASCII text file named MSL.INI, which
     should look like this:

    [msl]
        os2,     OS/2 References,     D:\BOOKS, 2011
        windows, Windows References,  D:\BOOKS, 2012
        net,     Network References,  D:\BOOKS, 2013
        msdos,   MS-DOS References,   D:\BOOKS, 2014
        msj,     MS Systems Journal,  D:\BOOKS, 4015
        hw,      Hardware References, D:\BOOKS, 4016
        c,       C References,        D:\BOOKS, 2017
        masm,    MASM References,     D:\BOOKS, 2018
        basic,   BASIC References,    D:\BOOKS, 2019
        pascal,  Pascal References,   D:\BOOKS, 2020
        fortran, FORTRAN References,  D:\BOOKS, 2021

  6. From the MSLIB directory on drive C:, type "MSL" to load Programmer's 
     Library and to run it as a standalone application. To load Programmer's 
     Library and run it as a memory-resident program, type "MSL /t":

                C:\MSLIB>msl <Enter>
             C:\MSLIB>msl -t <Enter>


See Appendix A in the User's Manual for more information on the individual
fields and format of the MSL.INI file.


=== ERROR MESSAGES

When you use the following commands, your work may be interrupted by an
error message.  If so, the following instructions will help you deal with
its associated problem.


==== CROSSREF, FIND, AND QUICKREF ERROR MESSAGES

Error message: "Too many cross-references" {BR}
-- Choose the OK button or press <Enter>.  {BR}
-- You have exceeded cross-reference capacity.  Save your current cross-
  reference location with a bookmark, choose View Bookmark, and then select
  the bookmark you just created.  This procedure clears the previous cross-
  references you've viewed.

Error message: "Unable to find datafiles"  {BR}
-- Choose the OK button or press <Enter>.  {BR}
-- Be sure the Programmer's Library disc is in your CD-ROM drive.


==== SEARCH ERROR MESSAGES

Error message: "No terms specified in search" {BR}
-- Choose the OK button or press <Enter>.     {BR}
-- Enter the word or phrase you want to search for in the Term box 
  and restart your search.


Error message: "Too many high frequency words.  Search canceled"
-- Choose the OK button or press <Enter>.  
-- Try redefining your search by using either fewer words in the Term 
  boxes or by using more specific words.


==== BOOKMARKS ERROR MESSAGES

Error message: "Can't save updated bookmark list"
  "      "   : "Can't open bookmark file for updating"
  "      "   : "Can't add any more bookmarks, delete one first" 
  "      "   : "Couldn't save bookmark file" 
  "      "   : "Couldn't open bookmark file"
  "      "   : "Bookmark not saved"

-- Choose the OK button or press <Enter>.

If any of the above messages appears, one of the following problems
  exists:

--  You have reached the bookmark capacity limit.  Delete unnecessary 
    bookmarks.

--  You have insufficient disk space on your computer.  Exit
    Programmer's Library and delete unnecessary files on your disk.

--  You have made your bookmark file (BKMARKS.INF) read-only.  Exit
    Programmer's Library, be sure you are in your \MSLIB directory,
    and then type:

         Attrib -r bkmarks.inf <Enter>

--  You do not have enough files specified in your CONFIG.SYS file.
    Exit Programmer's Library, and edit CONFIG.SYS to specify a larger
    "FILES =" value.

Error message: "Product not found"

-- Choose the OK button or press <Enter>.

-- Be sure an installed Microsoft CD-ROM Library disc is inserted in your
  CD-ROM drive.


==== "RE-RUN SETUP" 

When a file necessary to Programmer's Library operation is corrupted or
deleted, an error message prompts you to rerun setup.  First, delete the
file "MSL.VER", and then rerun setup for the product that was being used
when the error message was produced.  If you are using more than one
CD-ROM disc (for example, Programmer's Library, Small Business Consultant, and
Stat Pack) and you encounter another "rerun setup" error message, then
repeat the procedure for the disc that you were using when you encountered
the message.
