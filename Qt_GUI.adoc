== Qt GUI 图形应用框架

Qt Framework 是 Qt 公司（同名）开发一款跨平台 C++ 图形界面应用程序开发框架，广泛用于开发 GUI 程序，遵循 LGPL/GPL/商业许可协议，为开发者提供了丰富的 API 和工具，支持 Windows、macOS、Linux 等多种操作系统。

特色的信号与槽核心机制用于对象之间的通信。当某个事件发生时，对象会发射（emit）一个信号；如果有对象对这个信号感兴趣，并通过槽（slot）与之连接，那么当信号被发射时，槽就会被自动调用。

Qt Creator 是官方提供的集成开发环境（IDE），也支持跨平台开发。Qt Creator 支持多种编译器，如 GCC、MSVC 等。安装时，你需要选择或指定一个已安装的编译器。可以从官方网站获取配套软件信息：

• *Qt Framework*:  Cross-platform software libraries and APIs
• *Qt Development Tools*:  Qt Creator IDE and productivity tools
• *Qt Design Studio*:  UI Design tool for UI composition
• *Qt Accelerate*:  Qt Templates for industrial applications

Qt 支持以下核心机制，这些机制共同构成了 Qt 的灵活性和高扩展性，使其成为跨平台开发的理想选择。

• ​​信号与槽​​ 驱动业务逻辑。
• ​​元对象系统​​ 提供动态类型和属性支持。
• ​​事件系统​​ 处理用户输入和系统事件。
• ​​对象模型​​ 管理资源生命周期。
• ​​跨平台层​​ 实现多平台兼容。

核心机制说明如下：

1. 信号与槽（Signals & Slots），​实现对象间松耦合的通信。

** 信号：对象状态变化时发射的信号（如按钮点击）。
** 槽：响应信号的函数（如更新UI）。
** 直接连接（同步执行）：connect(sender, SIGNAL(sig()), receiver, SLOT(slot()))。
** 队列连接（异步执行）：Qt::QueuedConnection。
** 自动连接（默认）：根据对象父子关系决定。

2. 元对象系统（Meta-Object System）​​

• 元对象（Meta-Object）​​：
** 通过 moc（元对象编译器）生成，存储类的信号、槽、属性等信息。
** 每个 QObject 子类均有对应的元对象。
• 元方法（Meta-Method）​​：封装类中的方法（信号、槽、普通函数）。
• 属性系统（Property System）​​：支持动态读写属性（如 Q_PROPERTY(int value READ getValue WRITE setValue)）。
• ​​关键功能​​
** ​​动态类型信息​​：通过 QMetaObject::className() 获取类名。
** 动态调用方法​​：QMetaObject::invokeMethod()。
** 属性访问​​：QMetaProperty 提供属性的读写和通知机制。

3. 事件系统（Event System）​​

• ​事件处理流程​​
** ​​事件产生​​：系统或用户生成事件（如鼠标点击、键盘输入）。
** 事件分发：QCoreApplication::sendEvent() 或 postEvent()。
• ​​事件处理​​：
** 重写 event() 方法（通用处理）。
** 特定事件处理器（如 mousePressEvent()）。
• 事件过滤器（Event Filter）​​允许对象拦截其他对象的事件。
• 事件队列：默认异步处理（postEvent），可保证线程安全。
• ​​优先级控制​​：通过 installEventFilter 实现多层级过滤。

4. 对象模型（Object Model）​​

• ​​父子关系​​：通过 parent() 管理对象生命周期（父对象销毁时自动删除子对象）。
• ​​动态对象树​​：支持运行时动态添加/删除子对象。
• ​​对象名称​​：通过 setObjectName() 和 findChild() 实现对象查找。

5. 国际化（i18n）与本地化（L10n）​​

• ​​字符串提取​​：使用 lupdate 工具提取 .ts 文件。
• 翻译编译​​：lrelease 将 .ts 转换为 .qm 二进制文件。
• ​​运行时加载​​：通过 QTranslator 加载翻译文件。

6. 图形视图框架（Graphics View Framework）​​

• 场景（QGraphicsScene）​​：管理图形项（QGraphicsItem）。
• 视图（QGraphicsView）​​：显示场景内容，支持缩放、旋转。
• ​​坐标系转换​​：场景坐标、视图坐标、项目坐标。
​​• 性能优化​​
** ​​批量更新​​：使用 prepareGeometryChange() 减少重绘。
** ​​视口裁剪​​：自动剔除不可见区域的渲染。

7. 跨平台机制​​

• ​​平台抽象层 ​​QPA（Qt Platform Abstraction）​​：统一不同平台的输入、窗口系统接口。
• ​​平台插件​​：如 windows、xcb、wayland。

如果希望通过 Windows 环境变量设置来使用 MSYS2 子系统，那么就需要将子系统的 bin 路径放在 PATH 的前头，不建议这样做。VS Code 支持用户配置自定义终端，设置 terminal.integrated.profiles 添加新的终端类型。通过 Terminal: Select Default Profile 设置默认的终端。注意，MSYS2 的子系统入口（mintty）不支持作为 VS Code 集成终端来使用，也就是会以弹出新窗口的形式运行。可以使用 bash 加载配置脚本的形式来实现各个子系统环境的配置。

.VS Code 终端配置参考
[source,json]
----
    "terminal.integrated.defaultProfile.windows": "Bash UCRT64",
    "terminal.integrated.profiles.windows": {
        "Bash UCRT64": {
            "path": "C:/msys64/usr/bin/bash.exe",
            "args": [ "--init-file", "~/.bash_profile" ]
        },
        "Mintty UCRT64": {
            "path": "C:/msys64/usr/bin/mintty.exe",
            "args": [ "-c", "config" ]
        },
        "Msys64 UCRT64": {
            "path": "C:/msys64/ucrt64.exe"
        }
    }
----

https://github.com/tmux/tmux/wiki/[Tmux] 是一个终端复用器（terminal multiplexer），它允许用户在一个终端窗口中访问多个独立的会话。这个工具对于需要同时运行多个命令行程序的开发者和运维人员来说非常有用。Tmux 的核心功能是能够让会话（session）与窗口（window）分离，即使终端窗口被关闭，会话仍然可以在后台运行，之后可以重新接入这些会话。使用 pacman -S tmux 命令进行安装。

Key benefits of using Tmux include:

• **Resume remote sessions seamlessly** - Detach and reattach sessions as needed, even if disconnected.
• **Improved remote interactivity** - Keep applications and processes running remotely.
• **Advanced session control** - Tmux supports multiple windows and panes.
• **Enhanced productivity** - Manage multiple terminals efficiently from a single terminal.

Tmux 的主要特点

• 多会话支持：在一个窗口中同时访问多个会话。
• 会话分离与接入：允许用户分离会话并在需要时重新接入。
• 多人共享会话：每个会话可以有多个连接窗口，支持多人实时共享。
• 窗口拆分：支持窗口的垂直和水平拆分。

SSH 远程连接服务器操作任务中，有时会因为连接中断（掉线）而导致代码运行到一半被迫中断，服务器断掉失联后当前的进程也会被服务器给杀掉，之前的工作记录会丢失。Tmux 这款终端复用软件就可以用来解决这个问题。可以把当前操作的任务会话保存在服务器，即使和服务器断开连接，任务会话仍在服务器上继续执行着，当再次连接时，可以返回到之前保存的任务上继续进行操作。

Tmux 图形界面主要概念如下：

• 一个会话 (session) 包含多个窗口 (window)，一个窗口包含多个窗格 (pane)；
• 会话：工作环境配置，用户与机器的连接关系，可以临时断开（detact）或重新连接到服务器；
• 窗口：作为用户交互主界面——窗格的容器，每个窗口都可以容纳多个窗格；
• 窗格：在一个窗口中可以分成多个窗格，每个窗格相当一个 shell 程序；

=== Clang 编译器手动调用

注意引入头文件目录、导入库目录、导入库名称，并且要将导入库参数放在程序代码文件后面。GNU GCC 编译器 -I（include）用于添加头文件目录，使用位置比较自由，可以放到源程序文件的前面或后面。当然为了易读性，建议放到前面。参考 GCC 用户手册 3.15 Options for Linking。

链接库参数 -l（link）使用位置有依赖关系要求，此参数有 `-lLIBRARY` 和 `-l LIBRARY` 两种格式。这些库的顺序应该按照依赖关系排列，被依赖的库放在后面。例如，QtWidgets 依赖于 QtGui和 QtCore，所以应该先列出 QtWidgets，再列出 QtGui 和 QtCore。GCC 会将此参数直接发送给链接程序（linker），链接程序根据依赖顺序，从导入库目录中（-L）查找相应的文件。导入库的命名规则：-lQt6Core 对应的动态链接库文件为 libQt6Core.dll.a，用户不需要（也不可以）指定文件名的前缀、后缀。如果是静态链接（相对动态链接），使用的静态库（Static libraries），它是目标文件的归档格式，文件名后缀没有 dll 字样，比如 `libLIBRARY.a`。某些编译目标支持共享库（shared libraries），Windows 平台称动态链接库，​​共享库扩展名（.so/.dll）​。如果静态库可以共享库同时存在，GCC 优先使用共享库，除非使用 `-static` 进行静态链接。

构建图形界面应用需要给链接程序设置子系统选项，MSVC 使用 /subsystem:windows，GCC 则使用 -mwindows。

# 预处理资源文件
rcc -name resources resources.qrc -o qrc_resources.h

# 编译主程序
clang++ -std=c++17 \
    -IC:/msys64/ucrt64/include/qt6 \
    -IC:/msys64/ucrt64/include/qt6/QtWidgets \
    -IC:/msys64/ucrt64/include/qt6/QtGui \
    -IC:/msys64/ucrt64/include/qt6/QtCore \

GCC 编译时加 -g 参数产生的额外调试，优化选项会剔除调试信息，额外调试符号能让 gdb 调试工作更明了：

- `-g` 产生当前操作系统默认调试信息格式。
- `-ggdb` 产生 GDB 专用的调度信息格式。
- `-g3` 指定调试信息等级为 Level 3：
    - Level 0 不产生调试信息，默认 Level 2，所以 -g0 与 -g 不同。
    - Level 1 产生最小的调试信息，包括函数和外部变量的描述，以及行号表，但没有关于局部变量的信息。
    - Level 3 包含额外的信息，如 macro 定义，部分调试器支持 -g3 生成的宏扩展。
- `-gstabs` 生成 stabs 格式调试信息，但是不包括 gdb 专用的额外调试信息。
- `-gstabs+` 生成 stabs+ 格式调试信息，并且包含 gdb 专用的额外调试信息。

GCC optimization 优化选项：

- `-O0` 默认设置减少了编译时间，并且具有调试总是产生预期结果的效果。
- `-O1` 编译器试图减少输出二进制代码的大小和执行速度，但它不会执行可能大幅增加编译时间的优化。
- `-O2` 编译器执行的优化不需要以空间换取速度，增加了编译时间，但与 Level 1 相比，提高了性能。
- `-O3` 在 -O2 的基础上，打开更多的选项，这些选项还需要在速度上权衡空间。
- `-Ofast` 优化速度，无视严格的标准遵从性。
- `-Og` 调试体验优化，而不是空间或速度。
- `-Os` 空间优化，而不是速度。

MSYS2 环境下的 cmake 程序在配置项目过程出现以下错误：

[source,bash]
----
CMake Error at /ucrt64/lib/cmake/Qt6Core/Qt6CoreMacros.cmake:3019 (file):
  file RELATIVE_PATH must be passed a full path to the file:
  C:/msys64/ucrt64/lib/gcc/x86_64-w64-mingw32/14.2.0
Call Stack (most recent call first):
  /ucrt64/lib/cmake/Qt6Core/Qt6CoreConfigExtras.cmake:28 (_qt_internal_setup_deploy_support)
  /ucrt64/lib/cmake/Qt6Core/Qt6CoreConfig.cmake:142 (include)
  /ucrt64/lib/cmake/Qt6/Qt6Config.cmake:190 (find_package)
  CMakeLists.txt:8 (find_package)
----

根据提示，可以找到触发异常的配置脚本，错误是由一条 https://cmake.org/cmake/help/latest/command/file.html[file] 命令引起的。原因是 MSYS2 使用的路径与 Windows 使用的路径格式有差别。Windows 使用的盘符前缀 C: 包含的冒号 Linux 系统中作为路径分割符号使用。CMake 提供的 file 是一个多功能命令，除了用于读写 I/O 功能，还可以用于下载。出错脚本中则是使用了其中的路径转换功能。file(REALATIVE_PATH) 根据 <directory> 以及 <file> 得到一个相对路径，并保存到 <variable>。此问题无法使用 -DCMAKE_PREFIX_PATH=/ucrt64 这样的命令行参数修正。

检查 CMake 的详细输出，查看具体哪一步导致路径问题，可能需要启用 --debug-output 或 --trace。

****
TIP: GNU make 永远是你最纯粹的朋友！
****

[source]
----
Path Conversion
  file(REAL_PATH <path> <out-var> [BASE_DIRECTORY <dir>] [EXPAND_TILDE])
  file(RELATIVE_PATH <out-var> <directory> <file>)
  file({TO_CMAKE_PATH | TO_NATIVE_PATH} <path> <out-var>)
----

可以给 Qt 的配置脚本加入调试代码，或者使用以下脚本来重现问题，可以看到 Windows 风格的路径未能成功在 MSYS2 中安装的 CMake 运行。因此，问题属于移植过程中的平台兼容性问题，很难界定是 CMake 本身的问题还是 MSYS2 的问题，需要改用 CMake 官方提供的 Windows 版本。

[source]
----
# code -g /msys64/ucrt64/lib/cmake/Qt6Core/Qt6CoreMacros.cmake:3019

set(QT6_INSTALL_PREFIX "C:/msys64/ucrt64")
set(link_dir "C:/msys64/ucrt64/lib/gcc/x86_64-w64-mingw32/14.2.0")

set(QT6_INSTALL_PREFIX "/ucrt64")
set(link_dir "/C/msys64/ucrt64/lib/gcc/x86_64-w64-mingw32/14.2.0")

file(RELATIVE_PATH relative_dir "${QT6_INSTALL_PREFIX}" "${link_dir}")

message(relative_dir ==> ${relative_dir})
----

=== Qt Extension Modules

Qt Extension Modules bring additional functionality to Qt. They may be part of a given Qt release, but can deviate from the other Qt modules in terms of release schedule, platform support, the binaries Qt provides, commercial support, or compatibility promises. You can find specific details in the module documentation for each Extension Module.
